# ドキュメンテーションの基本原則

本ドキュメントは、本プロジェクトにおけるドキュメント作成・管理の基本原則を定義する。

---

## 1. 基本原則

### 原則① 文書は役割毎に分ける

1つの文書に複数の目的を詰め込まない。「誰が・何のために読むのか」を明確にし、読者と目的ごとに文書を分割する。役割が混在した文書は、AIにとってはノイズが増え、人間にとっては読みにくくなる。

### 原則② AI向け資料は小さく簡潔に

AIエージェントはコードを直接読めるため、コードから読み取れる内容を文書に重複させない。AI向け資料はコンテキストウィンドウに収まる小さな単位で、簡潔に保つ。冗長な文書はAIの判断精度をむしろ下げる。

### 原則③ 正本（Single Source of Truth）は絞る

同じ情報を複数の文書に書かない。情報ごとに正本となる文書を1つに定め、他の文書からは参照する。正本を絞ることで、更新漏れや文書間の矛盾を防ぐ。

---

## 2. AI向け設計書の考え方

**Why（なぜそうするのか）と What（何を実現するのか）を中心に書く。**

- How（どう実装するか）はコード自体が語るため、原則として書かない
- 実装時に迷いやすい**横断事項**だけを書く
  - 例: 命名規則、レイヤー間の依存ルール、エラーハンドリング方針、共通の制約条件
- 個別ファイルを読めば分かることは書かない
- 常に最新のコードと整合するよう、小さく保ちメンテナンスコストを下げる

## 3. 人間向け資料の考え方

**「多くのファイルを読まないと理解しにくい骨組みと重要事項」を中心に説明する。**

- システムの全体像・構成図
- 重要な設計判断とその背景（採用した理由・捨てた選択肢）
- アーキテクチャ（レイヤー構成、データフロー、コンポーネント間の関係）
- 中核となるアルゴリズムやドメインロジックの考え方

コードを1ファイルずつ読んでも見えてこない「構造」と「意図」を人間に伝えることが目的である。

## 4. ドキュメントカテゴリ

| # | カテゴリ | 配置場所 | 役割 |
|---|---------|---------|------|
| ① | アイディアドキュメント | `docs/ideas/` | AIとの議論・検討結果を残す。着想や比較検討の記録 |
| ② | AI向け設計書 | `docs/design/` | AIが実装時に参照する正本。WhyとWhat、横断事項を簡潔に記述 |
| ③ | 人間向け解説書 | `docs/human-review/` | 人間のレビュー・理解のための資料。全体像・設計判断・アーキテクチャを説明 |
| ④ | 修正指示書 | `docs/reviews/` | レビュー結果に基づく修正指示を記録 |
| ⑤ | ステアリング | `.steering/` | プロジェクト全体でAIの振る舞いを方向付ける指針 |
| ⑥ | AIエージェントのスキル | `.claude/skills/` | AIエージェントが利用する再利用可能な手順・ノウハウ |

---
## 5. 運用上の注意

- 文書を新規作成する前に、既存カテゴリのどこに属するかを必ず確認する
- 実装と design/ が乖離したら、design/ の更新を優先する（正本の鮮度を保つ）
- ideas/ は記録であり正本ではない。設計として確定した内容は design/ に移す
- AI向け文書が肥大化してきたら、削れる内容がないか定期的に見直す

## 6. 本プロジェクトでの当てはめ（2026-09-05）

4章の表に無い文書が3種類ある。**役割で判断し、置き場所を決めた。**

| 文書 | 場所 | 読者と役割 |
|---|---|---|
| `README.md` | リポジトリ直下 | **利用者向け。** 誰の何の問題を解決し、どう使い、何が不安か。開発の話は書かない |
| `CONTRIBUTING.md` | リポジトリ直下 | **開発者向け。** 手元での動かし方、構成、変更を送るまでの手順 |
| `.claude/rules/*.md` | — | **AI 向け（パス限定）。** `paths` に合うファイルを触ったときだけ読み込まれる。②の細則にあたる |

直下に置くのは、GitHub がその2つを特別扱いするからである
（README はトップに表示され、CONTRIBUTING は Issue と Pull Request の作成時に案内される）。

### 正本の割り当て

| 情報 | 正本 |
|---|---|
| **いまどこにいるか・次に何をするか** | `docs/human-review/roadmap.md` |
| 設計原則・不変条件 | `docs/design/principles.md` |
| 機能一覧（F-xx）とキー割り当て | `docs/design/features.md` |
| 非機能要件（NF-xx） | `docs/design/requirements.md` |
| コマンド一覧 | `CLAUDE.md`（開発者向けの抜粋を `CONTRIBUTING.md` に置く） |

**現在地を `README.md` や `CLAUDE.md` に書かない。** 必ずずれる。
2026-09-05 の刷新前は3箇所に書かれており、3つとも違う Phase を指していた。

### 節番号で参照しない

コード中のコメントが「設計書 8.6」のように章番号で参照していたため、
分割時に 92 箇所が迷子になりかけた。**新しく書くときは文書名か安定 ID
（`F-xx` `NF-xx` `R-xx` `PR-xx`）で参照する。** 章番号は動く。

### リンクは機械で検査する

`npm run lint` が `scripts/check-docs.mjs` を通す。
壊れた相対リンクと、正本の重複（現在地を2箇所に書く等）を弾く。
