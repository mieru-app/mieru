# データ形式と変換規則

**ここが本ツールの中核である。** ファイル形式・内部モデル・Markdown との相互変換・
正規化・ラウンドトリップ保証。変換規則を変えるときは必ずここを先に直す。

実装は `src/core/`。層ごとの細則は `.claude/rules/core-engine.md`。

**節番号は分割前のものを残してある。** コード中のコメントが
「設計書 8.6」のように章番号で参照しているため（49 ファイル・92 箇所）。
対応は [設計の索引](../design.md)。

## 6.1 ファイル形式仕様

1マップ = 1ファイル。文字コードは UTF-8（BOMなし）、改行は LF。

```markdown
---
title: 新規事業の論点整理
tags: [strategy, 2026Q3]
created: 2026-09-01T10:00:00Z
updated: 2026-09-01T14:32:00Z
mm:
  collapsed: ["1.0", "2.1"]
---

# 新規事業の論点整理

- 市場 🌏
  - TAM試算
    既存レポートでは1,200億円。ただし定義が広すぎる疑いがある。
    自社が取りうる範囲に絞ると300億円程度と見るのが妥当。
  - 競合の空白地帯
- 自社の強み 💪
  - 既存顧客基盤
- リスク ⚠️
  - 規制動向 → [[市場]]
```

#### frontmatter 仕様

| キー | 型 | 必須 | 説明 |
|---|---|---|---|
| `title` | string | ✓ | マップ名。ファイル名とは独立に保持する |
| `tags` | string[] | | 分類用タグ。マップ一覧での絞り込みに使用 |
| `created` | ISO8601 | ✓ | 作成日時（UTC） |
| `updated` | ISO8601 | ✓ | 最終更新日時（UTC） |
| `mm.collapsed` | string[] | | 折り畳み中ノードのパスID配列 |
| `mm.colors` | auto または string[] | | ブランチ配色。auto はブランチ順に既定パレットを適用 |

**原則2により、`mm` 配下以外に表示制御情報を置いてはならない。** AI出力時は frontmatter 全体を除去するため、本文だけが渡る。

#### 本文仕様

| 要素 | 記法 | モデル上の対応 |
|---|---|---|
| 中心テーマ | 最初の `# ` 見出し | ルートノード |
| 第1階層 | トップレベルの `- ` 箇条書き | ルートの子 |
| 第2階層以降 | 半角スペース2つでネストした `- ` | 各ノードの子 |
| 絵文字 | ラベル末尾の絵文字1文字 | `node.emoji` |
| ノート | 箇条書き直下のインデント段落 | `node.note` |
| 横断リンク | `[[対象ラベル]]` | `node.links` |

この書式は **markmap の記法と互換**である。したがって出力された `.md` は VSCode の Markdown Preview Enhanced や Obsidian の markmap プラグインでもそのままマインドマップとして描画できる。

## 6.2 内部データモデル

```typescript
/** マップ1件の完全な表現 */
interface MapDoc {
  meta: MapMeta;
  /** 中心テーマ。Markdown の H1 に対応する */
  root: MapNode;
  /** 表示状態。frontmatter の mm: に対応する */
  view: ViewState;
}

/** 一覧表示に必要な軽量メタ情報（本文を読まずに取得できる） */
interface MapMeta {
  id: string;          // ストア内での識別子（ローカル: ファイル名 / S3: オブジェクトキー）
  title: string;
  tags: string[];
  created: string;     // ISO8601
  updated: string;     // ISO8601
  version: string;     // 楽観ロック用。ローカル: 更新日時 / S3: ETag
}

interface MapNode {
  uid: string;         // セッション内でのみ有効な一時ID（永続化しない）
  path: string;        // 構造パスID 例: "1.0.2"。折り畳み状態の記録に使用
  label: string;       // 1〜3語のキーワード推奨
  emoji?: string;      // 絵文字1文字
  note?: string;       // 複数行可。AI出力時に本文段落として展開
  links: string[];     // 横断リンク先のラベル
  children: MapNode[];
}

interface ViewState {
  collapsed: string[];          // path の配列
  colors: "auto" | string[];
}
```

**ノードIDに関する設計判断:**
永続的なノードIDは Markdown 本文に書き込まない（原則2に反するため）。代わりに構造から導出される `path`（例: `1.0.2` = 第1ブランチの第0子の第2子）を用いる。

これにより、ノードを移動すると `mm.collapsed` に記録された折り畳み状態がずれる可能性がある。しかし実害は「折り畳み状態が少し変わる」だけであり、本文の可読性を守る利益がこれを上回ると判断する。

## 6.3 Markdown ⇄ モデル 変換規則

#### Markdown → モデル（読み込み）

| 入力 | 処理 |
|---|---|
| frontmatter | YAML として解析。`title` が無い場合は最初の H1 から補完 |
| 最初の `# X` | `root.label = X` |
| 2つ目以降の H1 | 第1階層ノードとして扱う（複数ルートは許容しない） |
| `## X` 〜 `###### X` | 見出しレベルに応じた階層ノード（markmap互換のため受理する） |
| `- X` / `* X` / `+ X` | 箇条書きノード。インデント量から階層を決定 |
| 箇条書き直下のインデント段落 | 直前ノードの `note` に格納。複数段落は改行2つで連結 |
| ラベル末尾の絵文字 | `emoji` に分離し `label` からは除去 |
| `[[Y]]` | `links` に Y を追加。**ラベル文字列からは除去しない**（可逆性のため） |
| 強調などのインライン記法 | ラベル文字列としてそのまま保持（解釈しない） |
| 見出し直下の地の文 | 直前のノードの `note` に格納する。破棄すると内容が失われるため |
| 空行・水平線・その他の要素 | 破棄（変換不可要素として警告を記録） |

**表は破棄されない（実測、2026-09-02）。** `remark-gfm` を導入していないため、パイプ表記は
表ではなく段落として解析される。結果として上の「地の文」の規則に乗り、`note` に逐語で格納されて
バイト単位で往復する。**GFM 拡張を追加すると、この性質が失われて表が破棄されるようになる。**
表を扱いたくなった場合でも `remark-gfm` は入れないこと。

**実際に破棄されるのは引用（`>`）とコードブロックのみである。** この2つも `note` へ逐語保持すれば
消えなくなるが、コードブロックは新しいエスケープ規則を要し 6.4 の改定を伴う（未決。`docs/ideas/2026-09-04-escape-roundtrip.md`）。

**インライン記法を「解釈しない」のは読み込みと保存の話であり、表示は別である（Phase 2.10 で追加）。**
`**強調**` はモデルにその文字列のまま保持され、そのまま出力される。この規則は変えない。
その上で、**画面に描くときにだけ**強調として見せる。保存形式に触れないため 6.5 の強保証に影響しない。
編集を始めたときは生の文字列を見せること。記号が見えないまま編集させると、利用者が気付かないうちに
記法を壊す。

## 6.4 正規化規則

出力の安定性（同じモデルからは常にバイト単位で同一の Markdown が生成される）を保証するため、以下を厳守する。

| 項目 | 規則 |
|---|---|
| 箇条書き記号 | `-` に統一 |
| インデント | 半角スペース2つ／階層 |
| ノート | 親箇条書きのインデント + 2スペースの段落として出力 |
| 見出し | 中心テーマの `# ` のみ。第1階層以降は全て箇条書きに正規化 |
| frontmatter キー順 | `title` → `tags` → `created` → `updated` → `mm` の固定順 |
| 空配列・未定義値 | frontmatter から省略する |
| 行末空白 | 除去 |
| ファイル末尾 | 改行1つで終端 |
| 絵文字 | ラベルの後に半角スペース1つを挟んで付与 |
| 改行コード | CRLF は LF に統一する |
| frontmatter の既定値 | `mm.collapsed` が空、`mm.colors` が `auto` の場合はキーごと省略する |
| ノートの各行 | 前後の空白を除去する。行頭の空白は Markdown ではインデントコードブロックに化け、逐語的に保持できないため |
| ノートの空行 | 連続する空行は1つにまとめる。箇条書きの継続が途切れるのを防ぐため |
| ラベルのみ空のノード | ノートの1行目をラベルへ繰り上げる。空の箇条書きの次行は継続行ではなく新しい段落として解析されるため |
| 空ラベルの箇条書き | 直前に空行を挿入する。空の箇条書きは段落を中断できず、親の遅延継続行として吸収されてしまうため |

**エスケープ規則（実装で確定）**

ラベル・ノートは元ソースを逐語的に切り出して保持するため、出力時のエスケープと読み込み時のアンエスケープが厳密に対でなければならない。片方だけを変更すると冪等性が崩れる。

| 対象 | 出力時 | 読み込み時 |
|---|---|---|
| `\` | `\` に二重化する | `\` + ASCII記号 のエスケープを解除する |
| 行頭の `#` `-` `*` `+` `>` | 直前に `\` を付ける | 同上 |
| 行頭の `1.` `1)` 等 | 記号の直前に `\` を付ける | 同上 |
| 行全体が `---` `***` `___` `=` 等 | 直前に `\` を付ける（`=` は1文字でも setext 見出しの下線になる） | 同上 |
| 行頭の `<tag` | 直前に `\` を付ける（HTMLブロックとして破棄されるのを防ぐ） | 同上 |
| 行頭の `[foo]:` | 直前に `\` を付ける（リンク参照定義として破棄されるのを防ぐ） | 同上 |
| 見出し行末尾の ` #` | `#` の直前に `\` を付ける（ATX 見出しの閉じシーケンスとして除去されるのを防ぐ） | 同上 |

**IMPORTANT: バックスラッシュのエスケープを先に行うこと。** 順序を逆にすると、行頭エスケープで足した `\` まで二重化される。

**frontmatter の引用符判定（実装で確定）**

YAML の数値・真偽値の文法を正規表現で判定してはならない。10進数だけでなく 16進（`0x0`）・8進（`0o7`）・特殊浮動小数（`.inf`）・桁区切り（`1_000`）なども数値として解釈され、文字列でなくなる。網羅を試みると必ず取りこぼす。

そのため**実際に使うパーサに判定させる**。引用符なしの候補を組み立てて読み戻し、元の文字列と一致し、かつエラー・警告が無い場合にのみ引用符を省く。

判定には `parse()` ではなく `parseDocument()` を使い、`errors` と `warnings` を自分で検査すること。`parse()` に `logLevel: "silent"` を渡すと**警告だけでなくエラーの送出まで抑止**され、`@` のような不正な平文がベストエフォートで通ってしまう。

なお YAML 1.1 の真偽値（`yes` / `no` / `on` / `off` / `y` / `n`）は YAML 1.2 では文字列だが、Obsidian など 1.1 で読むツールでは真偽値になる。相互運用のため引用符を付ける。

## 6.5 ラウンドトリップ保証（品質の生命線）

本ツールの信頼性はこの1点にかかっている。「開いて保存しただけで内容が変わる」ことは決して起きてはならない。

| 保証レベル | 内容 | 検証 |
|---|---|---|
| **強保証（必達）** | 正規化Markdown → モデル → Markdown が**バイト単位で一致**する（冪等性） | fast-check によるプロパティテスト。ランダム生成した木構造1万件で検証 |
| **弱保証** | 任意のMarkdown → モデル → Markdown は正規化されるため一致しない場合がある | 初回オープン時に差分がある場合、保存前にUIで明示的に通知する |

外部で作成された Markdown を初めて開いたときは、正規化により書式が変わりうる。この場合は保存操作の前に「書式が正規化されます（変更内容を表示）」という確認を1度だけ挟む。2回目以降は強保証の範囲に入るため確認しない。
