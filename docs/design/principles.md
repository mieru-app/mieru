# 設計原則と用語

**全ての設計判断はこの5原則に従う。判断に迷ったらここへ戻る。**
原則を変えたくなった場合は、実装より先にこの文書を直して合意を取ること。

**節番号は分割前のものを残してある。** コード中のコメントが
「設計書 8.6」のように章番号で参照しているため（49 ファイル・92 箇所）。
対応は [設計の索引](../design.md)。

---

## 原則1: Markdown が唯一の真実（Single Source of Truth）

内部データモデルは Markdown から導出される派生物であり、その逆ではない。保存されるのは常に Markdown 文字列である。

**帰結:** アプリが将来消滅してもデータは無傷。Git で差分が読め、思考の変遷を追える。Obsidian・VSCode・markmap とそのまま相互運用できる。

## 原則2: 表示状態を本文から隔離する

折り畳み状態・配色・座標といった「見た目の情報」は YAML frontmatter の `mm:` キー配下にのみ格納し、Markdown 本文には一切書き込まない。

**帰結:** AIに渡す本文が制御情報で汚れない。原則1と併せて、これが本ツールの中核的な設計判断である。

## 原則3: 保存先は単一のインターフェースの背後に隠す

UIコードは `MapStore` インターフェースのみを知る。ローカルフォルダかS3かを一切意識しない。

**帰結:** Phase 3 の同期機能追加が、UI・エディタ・変換ロジックに手を入れずに実装できる。

## 原則4: 入力速度が思考速度を妨げない

全ての主要操作をキーボードで完結させる。マウスは補助手段に留める。保存ボタンは設けず自動保存とする。

**帰結:** モーダルダイアログを原則禁止。設定項目は最小限に保つ。

## 原則5: ラベルとノートを分離する

ノードは「短いキーワード（ラベル）」と「任意の説明文（ノート）」の2層で構成する。キャンバス上にはラベルのみを表示し、ノートは Markdown 出力時に本文段落として展開される。

**帰結:** 「考えるときは軽く、AIに渡すときは濃く」が両立する。マインドマップ研究が示す「1ノード1〜3語」の原則と、AI入力に必要な文脈量の要求を同時に満たす。

---

## 4. 用語定義

| 用語 | 定義 |
|---|---|
| マップ | 1つのマインドマップ。1つの `.md` ファイルに1対1で対応する |
| ノード | マップを構成する要素。ラベル・絵文字・ノート・子ノードを持つ |
| ラベル | ノードの見出し。1〜3語の短いキーワードを推奨 |
| ノート | ノードに付随する説明文。キャンバスには表示されずAI出力時に展開される |
| 中心テーマ | マップのルートノード。Markdown の H1 に対応する |
| ブランチ | 中心テーマ直下の第1階層ノードとその配下の部分木 |
| 横断リンク | 親子関係を越えたノード間の関連。`[[ラベル]]` 記法で表現する |
| 正規化Markdown | 本ツールが出力する規定書式に従った Markdown（詳細は 6.4） |
| MapStore | 永続化層の抽象インターフェース（詳細は 8.1） |

## 破ってはいけない不変条件

上の5原則を、機械的に確かめられる形にしたもの。

1. **Markdown が保存形式である。** 独自形式や JSON でマップを保存しない（原則1）
2. **表示状態は frontmatter の `mm:` 配下にのみ書く。** 折り畳み・配色・座標を本文に書き込まない（原則2）
3. **UI 層は `MapStore` 経由でのみ永続化する。** File System Access API や GitHub API を `src/views/` から直接呼ばない（原則3）
4. **`mind-elixir` を import してよいのは `src/views/Canvas/` のみ**
5. **ラウンドトリップの強保証を壊さない。** 正規化 Markdown → モデル → Markdown はバイト単位で一致する（[データ形式](./data-format.md) 6.5）

3 と 4 は ESLint で機械的に強制している（[テスト戦略](./testing.md)）。

## 層の分け方

| 場所 | 役割 | 自動テスト |
|---|---|---|
| `src/core/` | Markdown とモデルの相互変換 | あり（プロパティテスト含む） |
| `src/store/` | `MapStore` と実装。永続化に触れるのはここまで | あり（FSA と IndexedDB の偽物を使う） |
| `src/state/` | 編集ロジック・状態・自動保存。React にも mind-elixir にも依存しない | あり |
| `src/app/` `src/views/` | React の描画と入力 | なし（手動試験） |

**描画層に判断を書かない。** 「このキーで何が起きるか」「保存すべきか」といった判断は
`src/state/` に置き、描画層はそれを呼ぶだけにする。UI を自動テストしない方針を採る以上、
判断が描画層に漏れた分だけ検証できない領域が増える。

例外として `src/app/keymap.ts`・`shortcuts.ts`・`command-palette.ts`・`edit-bar.ts` と
`src/views/Canvas/adapter.ts` は自動テストを持つ。キー割り当てとその表示は
「一覧が嘘をつくと復帰手段が無くなる」種類の情報であり、描画ではなく判断だからである。
