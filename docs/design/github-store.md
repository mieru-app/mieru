# GitHubStore

**保存がコミットになる保存先。** これによりスマートフォンから使えるようになり、
同時に**他人のトークンを預かる**ことになった（[セキュリティ](./security.md)）。

実測の記録は [GitHub API 事前検証](../human-review/github-api-verification.md)。

## 8.7 GitHubStore（Phase 2.6）

GitHub のリポジトリを保存先にする3つ目の `MapStore` 実装。
**目的はスマートフォン対応である**（Phase 2.7）。File System Access API は
デスクトップ版 Chromium にしか無く、保存先が無ければレスポンシブ対応だけしても使えない。

API の実挙動は着手前に実測してある。**数値と応答コードの正本は
[GitHub Contents API 事前検証メモ](../human-review/github-api-verification.md)** であり、
ここには設計上の決定だけを書く。

| 項目 | 仕様 |
|---|---|
| API | Contents API（`GET` / `PUT` / `DELETE /repos/{owner}/{repo}/contents/{path}`） |
| 認証 | Fine-grained PAT。利用者が入力し、ブラウザに保管する |
| `version` の実体 | Blob SHA。**git の blob ハッシュそのもの**で、内容だけで決まる |
| 保存の単位 | コミット1つ |
| 置き場所 | リポジトリ内の任意のフォルダ（既定はリポジトリ直下） |
| 通信 | ブラウザから `api.github.com` を直接呼ぶ。**中継サーバを持たない**（CORS が全面的に許可されていることを実測済み） |

#### 8.7.1 OAuth App を使わない理由

コールバックを受けるサーバが必要になり、「サーバレス（Lambda不使用）」という判断（12.4）と
衝突する。Fine-grained PAT なら**利用者が権限をリポジトリ単位で絞れ**、
アプリ側は文字列を預かるだけで済む。

#### 8.7.2 資格情報の保管とその代償

**IndexedDB に平文で保管する。** 置き場所は `src/store/github-auth.ts` に閉じる。

**暗号化しない。** 利用者に合言葉を毎回入力させない限り、復号鍵も同じブラウザに
置くことになり、鍵と錠前を並べて置くだけになる。**守っているように見えて守っていない
実装は、正直に平文で置くより悪い**（対策済みだと思い込ませるため）。合言葉の入力は
「スマートフォンから素早く開ける」という本来の目的と正面から衝突するので採らない。

**承知している危険が2つある。**

| 危険 | 内容 |
|---|---|
| XSS | 本ツールに XSS があれば、トークンは持ち出せる。**第三者スクリプトを一切読み込まない**ことが直接の対策になる（NF-43） |
| **同一オリジン** | GitHub Pages は `<名前>.github.io` が丸ごと1つのオリジンで、パスは境界にならない。**同じオリジンに置いた別のページから、この IndexedDB を読める。** 専用 Organization に分けたのはこのためであり、**そこに Mieru 以外を公開しないことが防御の本体**である（8.6・NF-44） |

**OSS として配る以上、預かるのは他人のトークンである。**
利用者は「配信元のオリジンを信用する」という判断を、多くの場合それと自覚せずに行う。
**だから危険を減らす責任は配信する側にあり、注意書きで肩代わりさせない。**

**そのうえで被害の上限も絞る。**

- Fine-grained PAT を**マップ置き場のリポジトリ1つだけ**に絞る（他のリポジトリへ波及しない）
- 権限は **Contents のみ**。Actions や Secrets には触れない
- 有効期限を付ける（切れたら入れ直す。`401` として利用者に伝わる）
- **接続の解除を1操作で行える**ようにし、押せば保管庫から消す
- **保管するかどうかを利用者に選ばせる。** 共用端末では記憶させない選択ができること。
  記憶しない場合はその場限りで、閉じれば消える

**この判断は NF-42 を字義どおりには満たさない**（10章）。`localStorage` ではないが
IndexedDB も平文であり、そこは言い換えでごまかさない。**Phase 3（Cognito）が
見送りになった以上、鍵を預かる主体がブラウザしか無い**ことを受け入れた上での判断である。

**README に同じ内容を書く。** OSS では、読んで確かめられることが信頼の根拠になる。
「サーバは無い」「トークンはあなたのブラウザにだけ入る」「ただし平文である」の3つを、
利用者が使い始める前に読める場所に置く。

#### 8.7.3 入力を受け取るときの判断

- **リポジトリは URL でも受ける。** 利用者はリポジトリ内のページを開いたまま
  アドレス欄をコピーしがちで、そこで弾かれる理由は本人には分からない
- **貼り付け損ねをその場で弾く。** 空白混じりや短すぎる値は、保存時になって初めて
  失敗すると原因が分からなくなる
- **保管の前に到達確認を行う。** `GET /repos/{owner}/{repo}` の応答で分ける

| 応答 | 意味 | 伝えかた |
|---|---|---|
| `401` | トークンが無効か期限切れ | 作り直しを促す |
| `404` | **「無い」と「権限が無い」の両方** | GitHub は権限の無いリポジトリの存在を伏せるため区別できない。**両方の可能性を伝える** |
| `403` | 残り回数が 0 なら上限、そうでなければ拒否 | ヘッダ `x-ratelimit-remaining` で分ける |
| `200` | 到達できた | `default_branch` を既定ブランチとして使う |

**これだけでは検査にならない**（2026-09-03 に実機で踏んだ）。`GET /repos/{owner}/{repo}` は
**Metadata 権限だけで通り、Metadata は GitHub が必須にしていて常に付く。**
つまり **Contents を付け忘れたトークンでも到達確認は成功する。**
そのまま通すと「接続できたのに最初の保存で初めて失敗する」という、
利用者が最も原因に辿り着けない壊れ方をする。

**したがって `GET /repos/{owner}/{repo}/contents/{置き場所}` を続けて投げる。**

| 応答 | 意味 |
|---|---|
| `200` / `404` | **合格。** 権限が無ければ `404` ではなく `403` が返るため、`404` は「権限はあるが、まだフォルダが無い」を意味する |
| `403` | **Contents 権限が無い。** 何をどこで直すか（Permissions → Contents → Read and write）まで伝える |

**読めることは書けることを保証しない。** Contents が Read-only のトークンはここを通り、
最初の保存で分かる。**そのときの文言を到達確認と同じにしてある**ので、
どちらで踏んでも利用者の次の行動は変わらない。

`200` の本文に `permissions.push` があれば書き込み可否が分かる。**無い場合は
「判定できなかった」として通す。**「書ける」と決めつけると、保存の失敗を到達確認が
保証したことになってしまう。

**書き込みで確認しない。** 確かめるには実際にコミットを作るしかなく、
検証用ファイルを置いて消すと利用者のリポジトリに履歴が残る。

#### 8.7.4 保存の前に条件付き GET を1回入れる（必須）

**`baseVersion` が `null` でないときは、`PUT` の前に
`If-None-Match: "<baseVersion>"` を付けた `GET` を1回投げる。**

| 応答 | 意味 | すること |
|---|---|---|
| `304` | 存在し、読んだときから変わっていない | そのまま `PUT` |
| `200` | 他所で変わっている | `ConflictError`（**本文はこの応答に入っている**） |
| `404` | 他所で削除された | `MapNotFoundError` |

**これが無いと 8.1 の契約表5行目を満たせない。** 実測のとおり、存在しないパスへ
`sha` 付きで `PUT` すると GitHub は `sha` を無視して `201` で作ってしまう。
つまり**他所で削除したマップを自動保存が黙って復活させる。**

副次的に2つ得をする。**競合時のサーバ本文がこの応答で手に入る**ため
（`409` の応答本文には内容が入らない）、`ConflictError` のために取り直さずに済む。
そして **`304` はレート枠を消費しない**ため、競合していない通常の保存では実質ただである。

`PUT` 側の `409` も `ConflictError` へ写して残す。この `GET` と `PUT` のあいだに
他所が書き込む可能性は消せないため、最後の砦として要る。

#### 8.7.5 保存間隔を保存先ごとに変える

GitHub のセカンダリ制限は**内容を作る要求が 80/分 かつ 500/時**である。
保存1回がコミット1つなので、**500/時 は平均7.2秒に1回が上限**という意味になる。
NF-03 の 800ms をそのまま当てると、集中して編集した1時間で上限に達する。

`MapStore` に推奨保存間隔を持たせ、`src/state/` の自動保存がそれに従う。
`LocalFolderStore` の 800ms は変えない（ローカル書き込みに上限は無い）。
内容が変わっていなければ Blob SHA も変わらないので、保存要求自体を省ける。

#### 8.7.6 保存先の選択は資格情報と別に持つ

**「どの保存先を使うか」と「GitHub の接続情報」を別の記録にする**
（`src/store/backend-preference.ts`）。一緒にすると、
**保存先を切り替えるたびにトークンを入れ直させる**ことになる。

| 操作 | 資格情報 | 選択 |
|---|---|---|
| GitHub に接続（記憶する） | 保存する | `github` |
| GitHub に接続（記憶しない） | **保存しない** | 記録しない（閉じれば消える） |
| ローカルフォルダに戻す | **残す** | `local` |
| 接続を解除する | **消す** | 消す |

**「記憶しない」を選べるようにする。** 共用の端末で使う人がいるためであり、
その場合トークンはこの実行中だけ生き、閉じた時点で消える。
既定は「記憶する」とする（毎回入力させるとスマートフォンでの利用が成立しないため）。

**File System Access API が使えないことは、もはや行き止まりではない。**
起動画面は「このブラウザでは使えません」で終わらせず、
**フォルダと GitHub の2つを並べて示す**（`StartScreen`）。

#### 8.7.7 `watch()` は当面持たない

`MapStore.watch?()` は任意メソッドであり、`GitHubStore` では実装しない。
**競合の検出は `write()` が担っており、データを失う経路は塞がっている。**
外部変更を能動的に知らせるのは利便であって安全ではない。

**実装するときの手段は分かっている。** ディレクトリ一覧にも `ETag` が付き、
`304` はレート枠を消費しないため、一定間隔で条件付き GET を投げるだけで
「何かが変わったか」を安価に判定できる。変わっていれば一覧の `sha` を
突き合わせて、変わったものだけ読み直す（8.7.4 と同じ仕組み）。
2.7（スマートフォン対応）で複数端末を行き来するようになってから要否を判断する。

#### 8.7.8 その他の実装上の制約

- **書き込み直後に読み直さない。** `GET` の応答には60秒のキャッシュが付く。
  `write()` の戻り値は `PUT` の応答に入る新しい `sha` から作る。
  読み直しが要る経路（8.7.4）には `cache: "no-store"` を付ける
- **`list()` は軽量にならない。** ディレクトリ一覧は `sha` を返すが `content` を返さず、
  `MapMeta` は frontmatter からしか作れないため 1 + N リクエストになる。
  一覧の `sha` を前回と突き合わせ、**変わったものだけ本文を取り直す**
- **`btoa()` を使わない。** Latin-1 しか扱えず日本語で例外になる。
  `TextEncoder` でバイト列にしてから base64 にする
