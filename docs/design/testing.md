# テスト戦略

**自動テストは変換エンジン（`src/core/`）に集中投下し、UI は手動試験に委ねる。**
個人ツールで UI の E2E を整備する費用対効果は低い一方、データ変質は取り返しがつかない。

層ごとの細則は `.claude/rules/*.md`。コマンドは `CLAUDE.md`。

**節番号は分割前のものを残してある。** コード中のコメントが
「設計書 8.6」のように章番号で参照しているため（49 ファイル・92 箇所）。
対応は [設計の索引](../design.md)。

## 7.2 コード品質の機械的強制

| ルール | 手段 |
|---|---|
| UI層は `MapStore` 以外の永続化APIを直接呼ばない（NF-51） | ESLint の `no-restricted-imports` で `src/views/**` からの FSA API / AWS SDK の import を禁止 |
| `mm` 配下以外に表示情報を書かない（原則2） | シリアライザの単体テストで検証 |
| mind-elixir への直接依存を局所化 | `src/views/Canvas/` 以外からの import を ESLint で禁止 |
| 型の厳格性 | `strict: true`、`noUncheckedIndexedAccess: true` |

## 7.3 各フェーズ共通の完了確認

各フェーズ終了時に以下を確認する。

1. DoD の全項目にチェックが入っている
2. `npm run build` / `npm run test` / `npm run lint` が全て成功する
3. 設計書との差異が発生していれば、設計書を更新している
4. 実データを使った動作確認を済ませている

## 全体実行の出力を捨てない

**`npm test` の出力は末尾だけを見ずに保存すること。**
fast-check は失敗時に種と反例を表示するため、出力さえ残っていれば再現できる。
**推測で候補を絞る前に、まず全文を残す。**

2026-09-02 に1件だけ落ちたテストの原因特定に2日かかったのは、
末尾しか残しておらず、落ちたテスト名を推測で埋めていたためである
（[記録](../ideas/2026-09-04-wbs-archive.md)）。
