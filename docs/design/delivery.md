## 8.6 配信（Phase 2）

PWA としてインストールするには HTTPS 配信が要る。Phase 2 では **GitHub Pages** を使い、Phase 3 で CloudFront へ移す。

| 項目 | 内容 |
|---|---|
| 配信元 | GitHub Pages（GitHub Actions でビルドして公開） |
| リポジトリ | 無料プランでは public が必要（private からの Pages は Pro 以上）。ソースに秘密情報は無いため問題にならない |
| base パス | 環境変数で切り替える。サブパス配信（`/<リポジトリ名>/`）と独自ドメイン（`/`）の両方を、コード変更なしで扱えるようにする |

**オリジンが変わると失われるもの。** PWA の同一性と IndexedDB はオリジン（スキーム + ホスト + ポート）に紐付く。本ツールは IndexedDB に作業フォルダのハンドルと退避データを置いているため、Phase 3 で配信元を変えると次が起きる。

- インストール済みアプリの入れ直し
- 作業フォルダの選び直し（権限が失効する）
- 退避データの喪失

**独自ドメインを用意すれば、この移行コストは消える。** Phase 2 で GitHub Pages にドメインを向け、Phase 3 で同じドメインを CloudFront へ向け替えれば、オリジンは変わらない。加えて `<ユーザー名>.github.io` は同一アカウントの他の GitHub Pages と**同一オリジンであり IndexedDB / localStorage を共有する**という問題も同時に解決する。

**当初の決定（Phase 2）: 独自ドメインを取得せず、`kyritk.github.io/mieru/` に置く。**
このとき同一オリジン問題は認識した上で受け入れていた。**保管していたのが自分のフォルダハンドルだけで、
盗まれて困る資格情報が無かったため**である。

#### 決定を改める（2026-09-03。OSS 配信を決めたことによる）

**専用の Organization `mieru-app` を作り、そこへ移す。**
配信先は `https://mieru-app.github.io/mieru/` とする。

前提が変わったのは1点だけで、そこが決定的である。**Phase 2.6 以降、この保管庫には
利用者のトークンが入る**（8.7.2）。しかも OSS として配ると、それは**他人のトークン**である。
「自分の鍵を自分の家に置く」から「他人の鍵を預かる」に変わった以上、
オリジンを他と共用したままにはできない。

| 案 | 判断 |
|---|---|
| **専用 Organization の直下に置く** | **採用。** Organization は無料でドメインも要らず、共用そのものが消える |
| 独自ドメインを取る | 採らない。費用と更新の手間が増えるうえ、上の案で同じ問題が解ける |
| 個人アカウントのまま注意して運用する | 採らない。**将来ページを1つ足すだけで破れる防御は防御ではない** |

**この配信先には Mieru 以外を publish しない。** 規則ではなく、これが唯一の防御である（NF-44）。

**直下（`/`）に置かないのは、パスがオリジンの一部ではないからである。**
`https://mieru-app.github.io/mieru/` と `https://mieru-app.github.io/` は
**同じオリジン**であり、守りたい性質（隣のページから保管庫を読まれない）は
どちらでも等しく満たされる。**直下配信で得られるのは URL の見た目だけ**で、
その対価にリポジトリ名を `mieru-app.github.io` にすることになる。
OSS として公開する以上、**人が見て star し clone するのはリポジトリ名**なので、
そちらを優先する。

| 項目 | 内容 |
|---|---|
| 配信元 | `https://mieru-app.github.io/mieru/`（Organization `mieru-app` の Pages。**2026-09-03 に移管済み**） |
| リポジトリ | `mieru-app/mieru`（`kyritk/mieru` を移管する） |
| `base` | `/mieru/`。**Actions が配信先の形から自動で決める**ので、手で書き換えない |

**移行の代償は「いま払う」。** オリジンが変わると PWA の入れ直し・作業フォルダの選び直し・
退避データの喪失が起きる（オリジン移管の代償。2026-09-03 に支払い済み）。**利用者が1人のうちなら1回のやり直しで済むが、
利用者が付いてから移すと全員に同じことを頼むことになる。**
2026-09-03 に実施した。

**移す前に旧オリジンを実測したところ、危険は仮定ではなかった。**
`kyritk.github.io` には Mieru 以外に2つの GitHub Pages が同居しており
（`petnews-editions` / `talkloop-legal`）、いずれも同一オリジンから
Mieru の IndexedDB を読める位置にあった。**当時それらは外部スクリプトを
SRI 付きで読み込んでおり実害は無かったが、防御が「隣のページが行儀よくあり続けること」
に依存していた**という点が問題であった。NF-44 を要件として置いた理由がこれである。

**フォークして自己ホストする場合の注意。** 自分の `<ユーザー名>.github.io` に置くと、
そこに同居する他のページと同一オリジンになる。**自己ホストが自動的に安全なわけではない。**
専用のアカウントか Organization を用意するか、そのオリジンに他を置かないこと。

その他の実装上の注意:

- `base` は環境変数で与えたままにする。配信先を変える判断をしても、コードを変えずに済むため
- IndexedDB のデータベース名は `mieru` で固定する
- **配信先を変えるときは、移行手順（PWA の入れ直しとフォルダの再選択）を利用者向けに用意すること。** 黙って権限が切れると「壊れた」ように見える

#### CSP — NF-43 を強制する（Phase 2.6 で追加）

**方針は破れるので、ブラウザに守らせる。** 「第三者スクリプトを読み込まない」は
心がけである以上、いつか誰かが解析ツールを1つ足す。**同一オリジンで動くコードは
本体と同じ権限を持つ**ため、その1行で利用者のトークンを読んで外部へ送れてしまう。

ビルド成果物の `<head>` 先頭に次を入れる（`vite.config.ts` の `contentSecurityPolicy`）。

```
default-src 'self'; connect-src 'self' https://api.github.com;
script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data:; font-src 'self';
object-src 'none'; base-uri 'none'; form-action 'none'
```

**本体は `connect-src` である。** 通信先を GitHub API だけに限れば、
**万一トークンを読まれても送り先が無い。** 「送らないと約束する」ではなく
「送れない」に変わる。

| 判断 | 理由 |
|---|---|
| `style-src` に `'unsafe-inline'` を許す | `mind-elixir` がスタイルを直接注入するため。**持ち出しに関わるのは `connect-src` と `script-src`** なので、防御の要は損なわれない |
| **開発サーバには入れない** | Vite は HMR のためにインラインスクリプト（`react-refresh`）と WebSocket を使う。**そこを許す書き方にすると本番の CSP まで緩む。** 緩めるより、ビルド時にだけ入れる |
| `frame-ancestors` を書かない | meta では効かない（HTTP ヘッダ専用）。GitHub Pages はヘッダを設定できないため、埋め込み防止は別の手段が要る。**未対応であることを承知しておく** |

**ローカルフォルダ運用にも効く。** トークンが無くても、フォルダの内容は読める状態にある。
`connect-src` はその持ち出しも同時に塞ぐ。

#### 実装（Phase 2 で追加）

| 項目 | 内容 |
|---|---|
| `base` | `BASE_PATH` 環境変数。既定は `/`。**専用 Organization の直下配信では既定のままでよい**（サブパス配信のときだけ Actions が渡す） |
| manifest | ビルド時に生成する（`vite.config.ts` の `webManifest`）。`start_url` と `scope` を `base` に合わせる必要があるため静的ファイルにできない |
| アイコン | `node assets/icon/generate.mjs` が `public/icons/` へ書き出す。`npm run dev` / `npm run build` が事前に実行する |
| Service Worker | `public/sw.js`。登録は本番ビルドのみ（`src/main.tsx`）。開発中に古い版を掴むと調査が空回りするため |
| 配信 | `.github/workflows/deploy.yml`。main への push で lint・テストを通してからビルドして公開する |

**Service Worker の方針は2つだけである。**

| 対象 | 方針 | 理由 |
|---|---|---|
| 画面遷移（HTML） | ネットワーク優先、失敗したらキャッシュ | 新しい版を配ったら次の起動で反映される |
| 同一オリジンの静的ファイル | キャッシュ優先、無ければ取得して蓄える | ファイル名にハッシュが入るので古い内容が混ざらない |

**どちらの経路でもエラー応答を蓄えない。** 配信先が変わって旧 URL が `404` になったとき、
それをアプリの起点として保存すると、**以後その 404 が「アプリ」として出続け、
利用者の側から復旧できなくなる。**

**オリジンを変えても、旧オリジンに入れた PWA は自動では消えない。**
利用者の手元では、Service Worker が抱えた旧版がそのまま動き続ける。
**配信先を変えるときは、旧 PWA を消して入れ直す手順を必ず案内すること**（PR-07）。

ライブラリを使わず手で書いてあるのは、方針がこの2つしかなく、
設定の面を増やす割に得るものが少ないためである。増やしたくなったら `vite-plugin-pwa` を検討する。
`rel="manifest"` の href は Vite の URL 書き換えの対象外なので、`%BASE_URL%` で自分で入れている。
