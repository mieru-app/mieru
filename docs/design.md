## 1. 背景と目的

### 1.1 背景

考えを整理する手段としてマインドマップを用いたい。加えて、整理した内容を**AIに読ませる入力ドキュメント**として活用したい。

既存のマインドマップツール（XMind, MindMeister 等）は独自形式で保存し、Markdown出力は劣化を伴う二次的なエクスポート機能である。そのため「整理する」と「AIに渡す」の間に必ず変換の手間と情報欠落が発生する。

### 1.2 目的

本ツールは **Markdown を保存形式そのものとする** ことでこの断絶を解消する。マインドマップの編集結果は常に人間可読な `.md` ファイルとして存在し、AIへの入力は「そのファイルを渡す」だけで完了する。

### 1.3 達成目標

| # | 目標 | 検証方法 |
|---|---|---|
| G-1 | マインドマップの作成・編集・管理ができる | Phase 2 完了時に実利用で評価 |
| G-2 | AI入力用Markdownをワンアクションで出力できる | Ctrl+Shift+C の1操作で完了すること |
| G-3 | Windows PCで快適に動作する | 1000ノードで60fps維持 |
| G-4 | スマートフォンでも編集できる | Phase 3 完了時 |
| G-5 | UI/UXがシンプルで使いやすい | モード2つ・ツールバー1本・モーダル原則禁止の遵守 |

## 2. スコープ

### 2.1 対象

- マインドマップの作成・編集・削除・一覧・検索
- キャンバス表示とアウトライン表示の相互切替、および Markdown そのものの表示（Phase 2.8）
- Markdown ファイルへの永続化（Phase 1: ローカルフォルダ / Phase 2.6: GitHub リポジトリ）
- テキスト出力（形式 × 範囲の2軸。7.3）と、AI からの取り込み指示のコピー（Phase 2.5）
- PWAとしてのインストールとオフライン動作
- スマートフォンからの編集（Phase 2.7。保存先を GitHub に置くことで成立する）
- 過去の版の閲覧と復元（Phase 2.8）
- Markdown 記法の描画（Phase 2.10。保存形式には影響しない）

### 2.2 対象外

| 項目 | 判断理由 |
|---|---|
| 複数人でのリアルタイム共同編集 | 単一利用者が要件。CRDT導入の複雑さに見合わない |
| 画像・添付ファイルの埋め込み | Markdownの可搬性を損なう。画像はURL参照のみ許容 |
| 手描き・自由配置キャンバス | ツリー構造の明快さが目的。Excalidraw等の代替が存在する |
| プレゼンテーション機能・印刷レイアウト | 目的が思考整理であり成果物提示ではない |
| AIによる自動マップ生成 | 「自分で考える」ことが目的のため意図的に除外（将来検討） |
| 課金・マルチテナント | 個人利用のため |

## 3. 設計原則

以降の全ての設計判断はこの5原則に従う。判断に迷った場合はこの節に立ち返る。

### 原則1: Markdown が唯一の真実（Single Source of Truth）

内部データモデルは Markdown から導出される派生物であり、その逆ではない。保存されるのは常に Markdown 文字列である。

**帰結:** アプリが将来消滅してもデータは無傷。Git で差分が読め、思考の変遷を追える。Obsidian・VSCode・markmap とそのまま相互運用できる。

### 原則2: 表示状態を本文から隔離する

折り畳み状態・配色・座標といった「見た目の情報」は YAML frontmatter の `mm:` キー配下にのみ格納し、Markdown 本文には一切書き込まない。

**帰結:** AIに渡す本文が制御情報で汚れない。原則1と併せて、これが本ツールの中核的な設計判断である。

### 原則3: 保存先は単一のインターフェースの背後に隠す

UIコードは `MapStore` インターフェースのみを知る。ローカルフォルダかS3かを一切意識しない。

**帰結:** Phase 3 の同期機能追加が、UI・エディタ・変換ロジックに手を入れずに実装できる。

### 原則4: 入力速度が思考速度を妨げない

全ての主要操作をキーボードで完結させる。マウスは補助手段に留める。保存ボタンは設けず自動保存とする。

**帰結:** モーダルダイアログを原則禁止。設定項目は最小限に保つ。

### 原則5: ラベルとノートを分離する

ノードは「短いキーワード（ラベル）」と「任意の説明文（ノート）」の2層で構成する。キャンバス上にはラベルのみを表示し、ノートは Markdown 出力時に本文段落として展開される。

**帰結:** 「考えるときは軽く、AIに渡すときは濃く」が両立する。マインドマップ研究が示す「1ノード1〜3語」の原則と、AI入力に必要な文脈量の要求を同時に満たす。

## 4. 用語定義

| 用語 | 定義 |
|---|---|
| マップ | 1つのマインドマップ。1つの `.md` ファイルに1対1で対応する |
| ノード | マップを構成する要素。ラベル・絵文字・ノート・子ノードを持つ |
| ラベル | ノードの見出し。1〜3語の短いキーワードを推奨 |
| ノート | ノードに付随する説明文。キャンバスには表示されずAI出力時に展開される |
| 中心テーマ | マップのルートノード。Markdown の H1 に対応する |
| ブランチ | 中心テーマ直下の第1階層ノードとその配下の部分木 |
| 横断リンク | 親子関係を越えたノード間の関連。`[[ラベル]]` 記法で表現する |
| 正規化Markdown | 本ツールが出力する規定書式に従った Markdown（詳細は 6.4） |
| MapStore | 永続化層の抽象インターフェース（詳細は 8.1） |

## 6. データ設計

### 6.1 ファイル形式仕様

1マップ = 1ファイル。文字コードは UTF-8（BOMなし）、改行は LF。

```markdown
---
title: 新規事業の論点整理
tags: [strategy, 2026Q3]
created: 2026-09-01T10:00:00Z
updated: 2026-09-01T14:32:00Z
mm:
  collapsed: ["1.0", "2.1"]
---

# 新規事業の論点整理

- 市場 🌏
  - TAM試算
    既存レポートでは1,200億円。ただし定義が広すぎる疑いがある。
    自社が取りうる範囲に絞ると300億円程度と見るのが妥当。
  - 競合の空白地帯
- 自社の強み 💪
  - 既存顧客基盤
- リスク ⚠️
  - 規制動向 → [[市場]]
```

#### frontmatter 仕様

| キー | 型 | 必須 | 説明 |
|---|---|---|---|
| `title` | string | ✓ | マップ名。ファイル名とは独立に保持する |
| `tags` | string[] | | 分類用タグ。マップ一覧での絞り込みに使用 |
| `created` | ISO8601 | ✓ | 作成日時（UTC） |
| `updated` | ISO8601 | ✓ | 最終更新日時（UTC） |
| `mm.collapsed` | string[] | | 折り畳み中ノードのパスID配列 |
| `mm.colors` | auto または string[] | | ブランチ配色。auto はブランチ順に既定パレットを適用 |

**原則2により、`mm` 配下以外に表示制御情報を置いてはならない。** AI出力時は frontmatter 全体を除去するため、本文だけが渡る。

#### 本文仕様

| 要素 | 記法 | モデル上の対応 |
|---|---|---|
| 中心テーマ | 最初の `# ` 見出し | ルートノード |
| 第1階層 | トップレベルの `- ` 箇条書き | ルートの子 |
| 第2階層以降 | 半角スペース2つでネストした `- ` | 各ノードの子 |
| 絵文字 | ラベル末尾の絵文字1文字 | `node.emoji` |
| ノート | 箇条書き直下のインデント段落 | `node.note` |
| 横断リンク | `[[対象ラベル]]` | `node.links` |

この書式は **markmap の記法と互換**である。したがって出力された `.md` は VSCode の Markdown Preview Enhanced や Obsidian の markmap プラグインでもそのままマインドマップとして描画できる。

### 6.2 内部データモデル

```typescript
/** マップ1件の完全な表現 */
interface MapDoc {
  meta: MapMeta;
  /** 中心テーマ。Markdown の H1 に対応する */
  root: MapNode;
  /** 表示状態。frontmatter の mm: に対応する */
  view: ViewState;
}

/** 一覧表示に必要な軽量メタ情報（本文を読まずに取得できる） */
interface MapMeta {
  id: string;          // ストア内での識別子（ローカル: ファイル名 / S3: オブジェクトキー）
  title: string;
  tags: string[];
  created: string;     // ISO8601
  updated: string;     // ISO8601
  version: string;     // 楽観ロック用。ローカル: 更新日時 / S3: ETag
}

interface MapNode {
  uid: string;         // セッション内でのみ有効な一時ID（永続化しない）
  path: string;        // 構造パスID 例: "1.0.2"。折り畳み状態の記録に使用
  label: string;       // 1〜3語のキーワード推奨
  emoji?: string;      // 絵文字1文字
  note?: string;       // 複数行可。AI出力時に本文段落として展開
  links: string[];     // 横断リンク先のラベル
  children: MapNode[];
}

interface ViewState {
  collapsed: string[];          // path の配列
  colors: "auto" | string[];
}
```

**ノードIDに関する設計判断:**
永続的なノードIDは Markdown 本文に書き込まない（原則2に反するため）。代わりに構造から導出される `path`（例: `1.0.2` = 第1ブランチの第0子の第2子）を用いる。

これにより、ノードを移動すると `mm.collapsed` に記録された折り畳み状態がずれる可能性がある。しかし実害は「折り畳み状態が少し変わる」だけであり、本文の可読性を守る利益がこれを上回ると判断する。

### 6.3 Markdown ⇄ モデル 変換規則

#### Markdown → モデル（読み込み）

| 入力 | 処理 |
|---|---|
| frontmatter | YAML として解析。`title` が無い場合は最初の H1 から補完 |
| 最初の `# X` | `root.label = X` |
| 2つ目以降の H1 | 第1階層ノードとして扱う（複数ルートは許容しない） |
| `## X` 〜 `###### X` | 見出しレベルに応じた階層ノード（markmap互換のため受理する） |
| `- X` / `* X` / `+ X` | 箇条書きノード。インデント量から階層を決定 |
| 箇条書き直下のインデント段落 | 直前ノードの `note` に格納。複数段落は改行2つで連結 |
| ラベル末尾の絵文字 | `emoji` に分離し `label` からは除去 |
| `[[Y]]` | `links` に Y を追加。**ラベル文字列からは除去しない**（可逆性のため） |
| 強調などのインライン記法 | ラベル文字列としてそのまま保持（解釈しない） |
| 見出し直下の地の文 | 直前のノードの `note` に格納する。破棄すると内容が失われるため |
| 空行・水平線・その他の要素 | 破棄（変換不可要素として警告を記録） |

**表は破棄されない（実測、2026-09-02）。** `remark-gfm` を導入していないため、パイプ表記は
表ではなく段落として解析される。結果として上の「地の文」の規則に乗り、`note` に逐語で格納されて
バイト単位で往復する。**GFM 拡張を追加すると、この性質が失われて表が破棄されるようになる。**
表を扱いたくなった場合でも `remark-gfm` は入れないこと。

**実際に破棄されるのは引用（`>`）とコードブロックのみである。** この2つも `note` へ逐語保持すれば
消えなくなるが、コードブロックは新しいエスケープ規則を要し 6.4 の改定を伴う（計画書 Phase 2.10 の未決）。

**インライン記法を「解釈しない」のは読み込みと保存の話であり、表示は別である（Phase 2.10 で追加）。**
`**強調**` はモデルにその文字列のまま保持され、そのまま出力される。この規則は変えない。
その上で、**画面に描くときにだけ**強調として見せる。保存形式に触れないため 6.5 の強保証に影響しない。
編集を始めたときは生の文字列を見せること。記号が見えないまま編集させると、利用者が気付かないうちに
記法を壊す。

#### モデル → Markdown（保存）

6.4 の正規化規則に厳密に従って出力する。

### 6.4 正規化規則

出力の安定性（同じモデルからは常にバイト単位で同一の Markdown が生成される）を保証するため、以下を厳守する。

| 項目 | 規則 |
|---|---|
| 箇条書き記号 | `-` に統一 |
| インデント | 半角スペース2つ／階層 |
| ノート | 親箇条書きのインデント + 2スペースの段落として出力 |
| 見出し | 中心テーマの `# ` のみ。第1階層以降は全て箇条書きに正規化 |
| frontmatter キー順 | `title` → `tags` → `created` → `updated` → `mm` の固定順 |
| 空配列・未定義値 | frontmatter から省略する |
| 行末空白 | 除去 |
| ファイル末尾 | 改行1つで終端 |
| 絵文字 | ラベルの後に半角スペース1つを挟んで付与 |
| 改行コード | CRLF は LF に統一する |
| frontmatter の既定値 | `mm.collapsed` が空、`mm.colors` が `auto` の場合はキーごと省略する |
| ノートの各行 | 前後の空白を除去する。行頭の空白は Markdown ではインデントコードブロックに化け、逐語的に保持できないため |
| ノートの空行 | 連続する空行は1つにまとめる。箇条書きの継続が途切れるのを防ぐため |
| ラベルのみ空のノード | ノートの1行目をラベルへ繰り上げる。空の箇条書きの次行は継続行ではなく新しい段落として解析されるため |
| 空ラベルの箇条書き | 直前に空行を挿入する。空の箇条書きは段落を中断できず、親の遅延継続行として吸収されてしまうため |

**エスケープ規則（実装で確定）**

ラベル・ノートは元ソースを逐語的に切り出して保持するため、出力時のエスケープと読み込み時のアンエスケープが厳密に対でなければならない。片方だけを変更すると冪等性が崩れる。

| 対象 | 出力時 | 読み込み時 |
|---|---|---|
| `\` | `\` に二重化する | `\` + ASCII記号 のエスケープを解除する |
| 行頭の `#` `-` `*` `+` `>` | 直前に `\` を付ける | 同上 |
| 行頭の `1.` `1)` 等 | 記号の直前に `\` を付ける | 同上 |
| 行全体が `---` `***` `___` `=` 等 | 直前に `\` を付ける（`=` は1文字でも setext 見出しの下線になる） | 同上 |
| 行頭の `<tag` | 直前に `\` を付ける（HTMLブロックとして破棄されるのを防ぐ） | 同上 |
| 行頭の `[foo]:` | 直前に `\` を付ける（リンク参照定義として破棄されるのを防ぐ） | 同上 |
| 見出し行末尾の ` #` | `#` の直前に `\` を付ける（ATX 見出しの閉じシーケンスとして除去されるのを防ぐ） | 同上 |

**IMPORTANT: バックスラッシュのエスケープを先に行うこと。** 順序を逆にすると、行頭エスケープで足した `\` まで二重化される。

**frontmatter の引用符判定（実装で確定）**

YAML の数値・真偽値の文法を正規表現で判定してはならない。10進数だけでなく 16進（`0x0`）・8進（`0o7`）・特殊浮動小数（`.inf`）・桁区切り（`1_000`）なども数値として解釈され、文字列でなくなる。網羅を試みると必ず取りこぼす。

そのため**実際に使うパーサに判定させる**。引用符なしの候補を組み立てて読み戻し、元の文字列と一致し、かつエラー・警告が無い場合にのみ引用符を省く。

判定には `parse()` ではなく `parseDocument()` を使い、`errors` と `warnings` を自分で検査すること。`parse()` に `logLevel: "silent"` を渡すと**警告だけでなくエラーの送出まで抑止**され、`@` のような不正な平文がベストエフォートで通ってしまう。

なお YAML 1.1 の真偽値（`yes` / `no` / `on` / `off` / `y` / `n`）は YAML 1.2 では文字列だが、Obsidian など 1.1 で読むツールでは真偽値になる。相互運用のため引用符を付ける。

### 6.5 ラウンドトリップ保証（品質の生命線）

本ツールの信頼性はこの1点にかかっている。「開いて保存しただけで内容が変わる」ことは決して起きてはならない。

| 保証レベル | 内容 | 検証 |
|---|---|---|
| **強保証（必達）** | 正規化Markdown → モデル → Markdown が**バイト単位で一致**する（冪等性） | fast-check によるプロパティテスト。ランダム生成した木構造1万件で検証 |
| **弱保証** | 任意のMarkdown → モデル → Markdown は正規化されるため一致しない場合がある | 初回オープン時に差分がある場合、保存前にUIで明示的に通知する |

外部で作成された Markdown を初めて開いたときは、正規化により書式が変わりうる。この場合は保存操作の前に「書式が正規化されます（変更内容を表示）」という確認を1度だけ挟む。2回目以降は強保証の範囲に入るため確認しない。

**検証状況（Phase 0 完了時点）:** プロパティテスト1万件が通過している。実装過程でこのテストが検出した往復破壊は6件（詳細は `docs/project-plan.md` の Phase 0 完了記録）であり、いずれも単体テストでは到達し得ない入力だった。

### 7.3 AI出力の3モード

「AIにインプットするドキュメントとして簡単に出力する」という要件の中核機能。

#### モード1: そのまま（Raw）

frontmatter を除去した本文をそのまま出力する。構造をコンパクトに伝えたいときに使う。

```markdown
# 新規事業の論点整理

- 市場 🌏
  - TAM試算
    既存レポートでは1,200億円。ただし定義が広すぎる疑いがある。
  - 競合の空白地帯
```

#### モード2: 見出し展開（Expanded）— 既定

第1〜第3階層を Markdown 見出し（`##` / `###` / `####`）に昇格させ、それ以降を箇条書き、ノートを本文段落として展開する。**LLMが最も文書として解釈しやすい形**であり、既定値とする。

```markdown
# 新規事業の論点整理

## 市場

### TAM試算

既存レポートでは1,200億円。ただし定義が広すぎる疑いがある。
自社が取りうる範囲に絞ると300億円程度と見るのが妥当。

### 競合の空白地帯

## 自社の強み

### 既存顧客基盤
```

#### モード3: 部分出力（Subtree）

選択中のノードを起点とする部分木のみを出力する。論点ごとに分けてAIに投げたい場合に使う。出力形式はモード2に準ずる。

#### 選び方を2軸に改める（Phase 2.5 で変更）

**上の3モードは、性質の違うものを1列に並べていた。** モード1と2は「どんな形式で書くか」、
モード3は「どこまでを出すか」であり、選択肢として同格ではない。実利用で「何を選べばよいか
分からない」という指摘が出たため、2つの軸に分解する。出力される Markdown 自体は変えない。

| 軸 | 選択肢 | 既定 |
|---|---|---|
| **形式** | 見出し（旧モード2） / 箇条書き（旧モード1） | 見出し |
| **範囲** | 全体 / 選択部分（旧モード3） | 全体 |

「見出し × 選択部分」は旧モード3に、「箇条書き × 全体」は旧モード1に等しい。
**新たに「箇条書き × 選択部分」が選べるようになる**が、これは分解の副産物であり
機能追加を目的としたものではない。

#### 名称（Phase 2.5 で変更）

ツールバーのボタンは「AI 用に出力」から**「テキスト出力」**へ改める。
「AI 用」は用途の説明であって動作の説明ではなく、押すと何が起きるかが伝わっていなかった。
出力先が AI であることは利用者が決めることであり、ボタンが名乗る必要はない。

#### 操作

| 操作 | 結果 |
|---|---|
| `Ctrl+Shift+C` | 既定（見出し × 全体）でクリップボードへコピー |
| ノード選択 + `Ctrl+Shift+C` | 見出し × 選択部分でコピー |
| ツールバーの「テキスト出力」 | 形式と範囲を選び、結果を見てからコピー／`.md` で保存 |

**出力パネルは結果をそのまま出す。** 選択肢の違いは説明より現物を見た方が早く、
何が渡るのか分からないまま貼り付けるのが、この道具でいちばん困る状況であるため。

#### 逆方向（Phase 2.5 で追加）

AI が整理した結果を Mieru で開けるよう、**Mieru が読める Markdown を書かせるための指示文**を
アプリからコピーできるようにする。置き場所は新規作成画面とする。出力パネルではない。
マップをまだ持っていない状態で使うものであり、出力パネルは開いているマップが前提だからである。

**指示文は文書ではなくコードに置く**（`src/state/import-prompt.ts`）。指示文に載せた例文が
実際に取り込めることを自動テストで確かめられるようにするためで、変換規則を変えたときに
指示文だけが古くなる食い違いが構造的に起きない。

## 8. 永続化設計

### 8.1 MapStore インターフェース

**原則3の実装。これが Phase 3 への移行コストを決定づける最重要の設計要素である。**

```typescript
interface MapStore {
  /** マップ一覧を取得する。本文は読み込まない（軽量） */
  list(): Promise<MapMeta[]>;

  /** マップ本文を取得する */
  read(id: string): Promise<{ md: string; version: string }>;

  /**
   * マップを保存する。
   * baseVersion は読み込んだ時点の version。
   * 不一致なら ConflictError を投げる（楽観ロック）。
   * 戻り値は保存後の新しい version。
   */
  write(id: string, md: string, baseVersion: string | null): Promise<string>;

  /** マップを削除する */
  remove(id: string): Promise<void>;

  /** 外部変更の監視（対応可能な実装のみ）。未対応なら no-op を返す */
  watch?(onChange: (id: string) => void): () => void;
}

class ConflictError extends Error {
  constructor(
    readonly id: string,
    readonly serverVersion: string,
    readonly serverMd: string,
  ) {
    super("Conflict on " + id);
  }
}
```

**UI層はこのインターフェースのみに依存する。** 実装の差し替えでフェーズ移行が完結する。

#### write() の契約（全実装が満たすこと）

| baseVersion | 保存先の状態 | 挙動 |
|---|---|---|
| `null` | 存在しない | 新規作成する |
| `null` | 存在する | `ConflictError`（他所で作成済み） |
| 版を指定 | 版が一致 | 上書きする |
| 版を指定 | 版が不一致 | `ConflictError` |
| 版を指定 | 存在しない | `MapNotFoundError`（他所で削除済み） |

この契約は共通の契約テスト（`src/store/__tests__/contract.ts`）として実装済みであり、`LocalFolderStore` / `S3Store` / `SyncingStore` を追加する際は同じスイートを流用して通すこと。楽観ロックの挙動が実装ごとにずれると、競合時にデータを失う。

### 8.2 実装バリエーション

| 実装 | Phase | version の実体 | 備考 |
|---|---|---|---|
| `MemoryStore` | 0 | 連番 | テスト用 |
| `LocalFolderStore` | 1 | 本文の内容ハッシュ | File System Access API |
| `GitHubStore` | 2.6 | Blob SHA | Contents API。保存はコミットになる |
| `S3Store` | 3 | S3 の ETag | ブラウザから直接S3を操作（見送り） |
| `SyncingStore` | 3 | S3 の ETag | 上2つを内包。IndexedDBをキャッシュとして使用 |

> **`LocalFolderStore` の version に更新日時を使わない理由（Phase 1 で変更）:** FAT32 / exFAT は更新日時の分解能が2秒あり、その窓に収まった外部編集を検出できずに黙って上書きしてしまう。`list()` も `read()` も frontmatter の取得のために本文を読むため、内容そのものをハッシュしても追加コストはほぼ無い。副次的な利点として、外部から**同じ内容**で書き直された場合に競合として扱わずに済む。ハッシュは変更検出専用であり暗号学的用途には使わない（`src/store/hash.ts`）。

### 8.3 LocalFolderStore（Phase 1）

```
利用者がフォルダを選択
  → FileSystemDirectoryHandle を取得
  → ハンドルを IndexedDB に保存（次回起動時に再利用）
  → 起動時に queryPermission() で権限を確認
     ├ granted → そのまま利用
     └ prompt  → 「フォルダへのアクセスを許可」ボタンを1回押してもらう
```

| 項目 | 仕様 |
|---|---|
| 対象ファイル | フォルダ直下の `*.md`（サブフォルダは Phase 2 で対応） |
| ID | ファイル名（拡張子含む） |
| 保存方式 | `createWritable()` に委ねる。Chromium は一時ファイルへ書き `close()` で差し替えるため、中断しても元ファイルは無傷で残る |
| 保存失敗時 | 指数バックオフで3回試行。権限失効は再試行せず即座に退避へ回す |
| 外部変更検知 | 30秒ごと、およびウィンドウフォーカス復帰時に更新日時を確認 |
| 権限失効時 | 編集内容をIndexedDBに退避し、再許可後に書き戻す |

**制約: File System Access API は Chromium系デスクトップブラウザ（Edge / Chrome / Opera）のみで動作する。** Firefox・Safari・全モバイルブラウザは非対応。Phase 1 の対応ブラウザがEdge/Chromeに限られるのはこのためであり、Phase 3 完了後にこの制約は解消される。

**改名（F-03）はファイル名の変更を伴う。** `MapStore` に「改名」は無く、
`write(新しい id)` と `remove(古い id)` の2手で行う（`src/state/workspace.ts` の `renameMap`）。
**必ず書いてから消す。** 逆順にすると、消した後で書き込みに失敗したときにマップそのものが失われる。
この順序であれば、失敗しても残るのは同じ内容の2ファイルであり、利用者が片方を消せば復旧できる。

改名は内容を読み直して `title` と H1 を書き換え、正規化を通して書き戻す。
アプリの外で書かれた Markdown は整形され直すが、これは保存のたびに起きることであり
改名に固有の副作用ではない。

### 8.4 S3Store（Phase 3）

```
S3キー設計:
  s3://mieru-data/users/{cognito-identity-id}/maps/{uuid}.md

  ・ファイル名ではなくUUIDをキーにする（改名時にオブジェクトを移動せずに済む）
  ・表示名は frontmatter の title から取得する
  ・一覧は ListObjectsV2 + オブジェクトメタデータで取得する
```

| 操作 | 実装 |
|---|---|
| `list()` | `ListObjectsV2` でキー・更新日時・ETagを取得。title/tags はオブジェクトのユーザー定義メタデータに複製して保持し、本文取得を回避する |
| `read()` | `GetObject`。ETag を version として返す |
| `write()` | `PutObject` に `If-Match: {baseVersion}` を付与。412 応答なら `ConflictError` |
| `remove()` | `DeleteObject` |

> **要検証（Phase 3 着手時）:** S3 の条件付き書き込み（`PutObject` の `If-Match`）の利用可否と対象リージョンでの対応状況を実装前に確認すること。利用できない場合は「ETag比較 → 書き込み」の2段構えにフォールバックし、競合検出の窓が僅かに残ることを許容する（単一利用者のため実害は限定的）。

### 8.5 SyncingStore と競合解決（Phase 3）

```
       編集
        ↓
   IndexedDB（即座に書き込み・オフラインでも動作）
        ↓ デバウンス / オンライン復帰時
   S3 へ push（If-Match で楽観ロック）
        ↓ 412 が返った場合
   ┌──────────── 競合解決 ────────────┐
   │ 1. サーバ版を取得                 │
   │ 2. ローカル版を                   │
   │    「{title} (競合 2026-09-01)」  │
   │    として別マップに保存            │
   │ 3. UIで両者の差分を提示し選択させる │
   └──────────────────────────────────┘
```

**設計方針: データを失わないことを最優先する。** 自動マージは行わない。競合時は必ず両方を残し、判断は利用者に委ねる。単一利用者の複数端末間という状況では競合の発生頻度自体が低く、複雑な自動解決（CRDT等）を導入する費用対効果がないと判断する。

### 8.6 配信（Phase 2）

PWA としてインストールするには HTTPS 配信が要る。Phase 2 では **GitHub Pages** を使い、Phase 3 で CloudFront へ移す。

| 項目 | 内容 |
|---|---|
| 配信元 | GitHub Pages（GitHub Actions でビルドして公開） |
| リポジトリ | 無料プランでは public が必要（private からの Pages は Pro 以上）。ソースに秘密情報は無いため問題にならない |
| base パス | 環境変数で切り替える。サブパス配信（`/<リポジトリ名>/`）と独自ドメイン（`/`）の両方を、コード変更なしで扱えるようにする |

**オリジンが変わると失われるもの。** PWA の同一性と IndexedDB はオリジン（スキーム + ホスト + ポート）に紐付く。本ツールは IndexedDB に作業フォルダのハンドルと退避データを置いているため、Phase 3 で配信元を変えると次が起きる。

- インストール済みアプリの入れ直し
- 作業フォルダの選び直し（権限が失効する）
- 退避データの喪失

**独自ドメインを用意すれば、この移行コストは消える。** Phase 2 で GitHub Pages にドメインを向け、Phase 3 で同じドメインを CloudFront へ向け替えれば、オリジンは変わらない。加えて `<ユーザー名>.github.io` は同一アカウントの他の GitHub Pages と**同一オリジンであり IndexedDB / localStorage を共有する**という問題も同時に解決する。

**決定: 独自ドメインは取得しない（Phase 2 時点）。** Phase 3 で CloudFront へ移す際の入れ直しを一度受け入れる。
作業は数分で済み、失われるのは「どのフォルダを使っていたか」の記憶だけである（マップ本体はローカルフォルダにあり無関係）。

この決定に伴う実装上の注意:

- 配信は `https://<ユーザー名>.github.io/<リポジトリ名>/` のサブパスになる。Vite の `base` と PWA の `scope` / `start_url` をこれに合わせる
- `base` は環境変数で与える。独自ドメインへ移す判断をしても、コードを変えずに切り替えられるようにしておく
- 同一オリジンに自分の他の GitHub Pages が同居する。IndexedDB のデータベース名は `mieru` で固定し、他プロジェクトと衝突させない
- **Phase 3 の着手時に、移行手順（PWA の入れ直しとフォルダの再選択）を利用者向けに用意すること。** 黙って権限が切れると「壊れた」ように見える

#### 実装（Phase 2 で追加）

| 項目 | 内容 |
|---|---|
| `base` | `BASE_PATH` 環境変数。既定は `/`。GitHub Actions が `/<リポジトリ名>/` を渡す |
| manifest | ビルド時に生成する（`vite.config.ts` の `webManifest`）。`start_url` と `scope` を `base` に合わせる必要があるため静的ファイルにできない |
| アイコン | `node assets/icon/generate.mjs` が `public/icons/` へ書き出す。`npm run dev` / `npm run build` が事前に実行する |
| Service Worker | `public/sw.js`。登録は本番ビルドのみ（`src/main.tsx`）。開発中に古い版を掴むと調査が空回りするため |
| 配信 | `.github/workflows/deploy.yml`。main への push で lint・テストを通してからビルドして公開する |

**Service Worker の方針は2つだけである。**

| 対象 | 方針 | 理由 |
|---|---|---|
| 画面遷移（HTML） | ネットワーク優先、失敗したらキャッシュ | 新しい版を配ったら次の起動で反映される |
| 同一オリジンの静的ファイル | キャッシュ優先、無ければ取得して蓄える | ファイル名にハッシュが入るので古い内容が混ざらない |

ライブラリを使わず手で書いてあるのは、方針がこの2つしかなく、
設定の面を増やす割に得るものが少ないためである。増やしたくなったら `vite-plugin-pwa` を検討する。
`rel="manifest"` の href は Vite の URL 書き換えの対象外なので、`%BASE_URL%` で自分で入れている。

### 9.2 IAMポリシー（認証済みロール）

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OwnObjectsOnly",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::mieru-data/users/${cognito-identity.amazonaws.com:sub}/*"
    },
    {
      "Sid": "ListOwnPrefixOnly",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::mieru-data",
      "Condition": {
        "StringLike": {
          "s3:prefix": ["users/${cognito-identity.amazonaws.com:sub}/*"]
        }
      }
    }
  ]
}
```

`${cognito-identity.amazonaws.com:sub}` はIAMがリクエスト時に実際のIdentity IDへ置換する変数である。これにより**利用者は自分のプレフィックス配下以外に一切アクセスできない**。アプリ側のコードにバグがあっても他者のデータには到達しない。

## 11. エラー処理方針

| 事象 | 挙動 |
|---|---|
| フォルダ権限の失効 | 編集内容をIndexedDBへ退避 → ステータスバーに再許可ボタンを表示 → 許可後に自動で書き戻す |
| ファイルの外部変更を検知 | ステータスバーに通知。未編集なら自動再読込、編集中なら「再読込 / 自分の版を保持」を選択させる |
| 変換不可な要素を含むMarkdown | 該当要素は破棄する。**警告表示は行わない（2026-09-02 変更）** — 下記 |
| 保存失敗 | 3回まで指数バックオフで再試行。それでも失敗したらIndexedDBへ退避しエラーを表示 |
| 競合（Phase 3） | 8.5 に従い両方を保持 |
| 非対応ブラウザ | 起動時に検出し、対応ブラウザを案内する画面を表示（Phase 1のみ） |

**共通方針: 利用者の入力を失わせる挙動は、いかなる場合も許容しない。** 保存できない状況ではまずIndexedDBへ退避することを最優先とする。

**変換警告を表示しないと決めた経緯（2026-09-02）**

初版はこの警告を必須としていたが、実装されないまま Phase 2 まで来た。改めて検討した結果、
利用者判断により**実装しないこととした。** 利用者が1人であり、警告を読む手間に見合わないためである。

**ただし共通方針との緊張は残っている。** 実際に破棄されるのは引用（`>`）とコードブロックであり
（6.3 の実測）、これらは黙って消える。警告を出さない以上、消えることを防ぐ手段は
**逐語保持しかない**（計画書 Phase 2.10 の未決）。実利用で困った時点でそちらに着手する。
**「警告しない」は「消えてよい」ではない。**

`parse()` は現在も `warnings` を正しく積んでいる。UI が使わないだけであり、
方針を戻す場合に実装し直す必要があるのは表示側のみである。

## 12. 技術選定の根拠

### 12.1 キャンバスライブラリ: mind-elixir を採用

| 候補 | 最新版 | 評価 | 判断 |
|---|---|---|---|
| **mind-elixir** | 5.15.1（安定） | MIT。編集・キーボード操作・折り畳み・横断リンクを内蔵。フレームワーク非依存。活発に更新（2026-08時点） | **採用** |
| markmap | 0.18.12 | MIT。Markdown→マインドマップの描画品質は高いが**表示専用で編集不可** | 不採用。ただし記法互換の参照元とする |
| @xyflow/react | 12.11.5 | 汎用ダイアグラム。自由度は最大だがマインドマップのレイアウト・操作を全て自作する必要がある | 不採用（工数過大） |
| jsmind | 0.9.1 | 実績はあるがUIが古く、更新頻度が低い | 不採用 |

**バージョン固定の注意:** mind-elixir は 6.0.0 系がプレリリース中であり、npm の `latest` タグが `6.0.0-next.4` を指すという異常な状態にある（dist-tags: latest=6.0.0-next.4, beta=6.0.0-next.5）。安定版の `5.15.1` を `package.json` で厳密に固定し、6.0 系の安定版リリース後に計画的に移行する。

**ロックイン対策:** データは Markdown であり mind-elixir に依存しない。将来このライブラリを捨てても、描画層を差し替えるだけで済む。これは原則1が生む副次的な利益である。

### 12.2 Markdownシリアライザを自前実装する理由

`remark-stringify` は箇条書き記号やインデント量の出力が設定と入力に依存して揺れる。6.5 の強保証（バイト単位の冪等性）を達成するには出力を完全に制御する必要があるため、解析には `remark-parse` を使い、生成のみ自前で実装する。

### 12.3 CRDT（Yjs等）を採用しない理由

CRDTはリアルタイム共同編集のために設計された技術であり、データモデルに相応の複雑さを持ち込む。本ツールは単一利用者が自分の複数端末で使うことを想定しており、同時編集の発生頻度は極めて低い。8.5 の「両方を保持して利用者に選ばせる」方式で必要十分であり、費用対効果が見合わない。

### 12.4 サーバレス（Lambda不使用）とする理由

データが単純なファイルであり、認可はIAMポリシーで宣言的に表現できる。サーバコードを書かないことで、実装工数・障害点・運用負荷・コストの全てが削減される。将来、全文検索の高速化等でサーバ側処理が必要になった時点で追加すればよい。

### 12.5 名称: Mieru（Phase 2 着手時に確定）

「見える」＝「考えが見えるようになる」で、名前と道具の価値が一致する。3音で呼びやすい。既存の同名ソフトはあるが全て別カテゴリ（プロキシ、OCR、通訳）で、マインドマップ領域には無い。

不採用: **OpenMind.md** ——同じマインドマップ領域に既存の OpenMind が複数実在する（Microsoft Store 等）。**MDMind** ——識別性は最高だが `MD` の第一想起が Medical Doctor で響きが弱い。

**残る懸念:** ホワイトボードツール Miro と英字表記で1文字違い。日本語では明確に異なるが、一般公開時は混同の可能性を考慮する。

**商標（2026-09-02 調査）:** J-PlatPat に「MIERU」の出願が1件（商願2025-122872、**登録ではなく審査中**、株式会社コラボフィット）。ただし指定商品は第9類の**眼鏡類のみ**（類似群 10B01・23B01）。第9類は眼鏡からソフトウェアまでを含む広い区分であり、類否は類似群コードで判断される。ソフトウェアの 11C01 も第42類の 42X11 も含まれないため、**本ツールとは抵触しない**。

> カタカナ「ミエル」・平仮名「みえる」および第42類は未調査。個人利用と無償配布の範囲では商標権が及ばない（業としての使用に及ぶ）が、収益化する場合は着手前に弁理士による調査を行うこと。

### 12.6 アイコン: 「放射する光条」（Phase 2 着手時に確定）

文字マーク「M」を白抜きにして暗い地の中心に置き、その外側から5色の光条を放射させる。中心から枝が伸びるというマインドマップの構造がそのまま図案になっている。生成は `assets/icon/generate.mjs`（SVG と PNG を `assets/icon/dist/` へ書き出す）。

**最初の案が失敗した理由を規則として残す。** 白い M を載せるために5色すべての明度を揃えた結果、輝度が 10.7〜17.8% に収まり、隣り合う面のコントラスト比が 1.06〜1.29:1 になった。**色相が違っても明るさが同じ色は互いに見分けられない**（等輝度）。色は付いているのに境界が消え、濁って見える。

| 規則 | 理由 |
|---|---|
| 明るさの役割を分ける。地は徹底して暗く、色は地の上に置く | 白抜きの文字と鮮やかな色を両立させる唯一の方法。地と白の比 19:1、地と色の比 4.2:1 以上 |
| 色どうしを直接隣接させない。あいだに地を挟む | 境界のコントラストが常に高くなり、等輝度の隣接を構造的に避けられる |
| 面積を不均等にする（およそ 7:3） | 補色に近い色を同量で使うと互いに打ち消し合う |
| 色数を増やしすぎない | 16px では1色あたり数ピクセルしか残らない |
| グレースケールで形が残るか確認する | 明度だけで成立していれば、小さくしても色覚特性が異なる人にも崩れない |

| 用途 | 値 |
|---|---|
| 地 / `theme_color` | `#0A0F1F` |
| 光条 | 青 `#2F6BFF` / シアン `#00C2D1` / 橙 `#FF6A00` / 桃 `#FF2D6F` / 紫 `#9B5CFF` |
| 光条の角度 | 10-64° / 78-116° / 132-198° / 214-256° / 274-346°（真上を 0 として時計回り） |
| 光条の内半径 | 215（M の外接半径 約198 より大きく取り、文字に色を掛けない） |
| 書き出し | 192・512（`any`）、512（`maskable`、図案を 0.82 倍して余白を確保）、apple-touch 180、favicon 32/16 |

光条の幅は不揃いにしてある。均等に割ると回る風車に見えて散漫になるため。
16px での実効面積は 地 47.7% / M 12.5% / 紫 14.8% / 青 8.2% / 橙 7.0% / 桃 7.0% / **シアン 2.7%（7px）**。
5条すべてが残るが、最も細いシアンは 7px しかない。光条の角度を変えるときはこの値を再測すること。

`any` と `maskable` はファイルを分ける（`"any maskable"` と1つにまとめない）。
