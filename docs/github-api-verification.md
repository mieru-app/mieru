## 1. なぜ実装より先にこれを置いたか

設計書 8.1 の `write(id, md, baseVersion)` は「`baseVersion` が保存先の現在の版と
不一致なら `ConflictError`」という契約を持つ。`GitHubStore` はこれを Blob SHA で
満たす計画である（計画書 4章）。

**この2点が崩れると `GitHubStore` は成立しない。**

1. Blob SHA が楽観ロックとして機能するか（不一致を GitHub 側が拒めるか）
2. Blob SHA が内容に対して安定か（同じ内容なら常に同じ値になるか）

実装を書いてから崩れると、認証・UI まで含めて組み直しになる。先にここだけを確かめる。

---

## 2. 実測して確定したこと（資格情報なし）

公開リポジトリ `kyritk/mieru` への未認証の読み取りだけで確かめた。

### 2.1 `sha` は git の blob ハッシュそのものである ✅

API が返した `content` を base64 復号し、`sha1("blob " + 長さ + "\0" + バイト列)` を
計算すると、API の `sha` と完全に一致した。

| ファイル | サイズ | API の sha | 再計算した blob ハッシュ | 一致 |
|---|---|---|---|---|
| `README.md` | 4,286 B | `aad3c4b0f7a71ea9…` | `aad3c4b0f7a71ea9…` | ✅ |
| `docs/design.md` | 59,676 B | `2623d08c246fa23d…` | `2623d08c246fa23d…` | ✅ |

どちらも日本語（非 ASCII）を含む。**`version` はサーバが振る不透明な値ではなく、
内容だけで決まる関数である。** これで疑問2は片付いた。

### 2.2 その帰結

**同じ内容なら、パスが違っても、コミットが違っても、時刻が違っても同じ SHA になる。**
`git hash-object` で内容 `x` の別ファイル2つを取ると、いずれも
`c1b0730e0133447badcfd47fd144e254807b06e1` になる。

これは `LocalFolderStore` が内容ハッシュを version にしているのと**同じ性質**であり
（設計書 8.2 の注記）、副次的な利点もそのまま受け継ぐ。

- 外部から**同じ内容**で書き直されても競合にならない
- 逆に、A → B → A と戻された場合は元の version に戻る（いわゆる ABA）。
  ただし戻った先の内容は自分が読んだ内容と同一なので、上書きしても失うものが無い。
  `LocalFolderStore` と同じ理屈で受容できる

### 2.3 ファイル取得の ETag は blob SHA と同じ値だった ✅

`GET /contents/README.md` の応答ヘッダは `ETag: "aad3c4b0f7a71ea9…"` で、
**同じ応答の `sha` と一致した。**

つまり `If-None-Match: "<version>"` を付けて投げれば、
**本文を転送せずに「変わっていない」を確認できる。** `watch?()` の実装手段になる。

ただし**未認証では 304 も枠を消費した**（`X-RateLimit-Used` が 14 → 16、
2回の 304 で2消費）。認証時に同じかは 5章で確かめる。

### 2.4 GET には60秒のキャッシュが付く ⚠️

```
Cache-Control: public, max-age=60, s-maxage=60
```

**ブラウザの `fetch()` はこれに従う。** 書き込んだ直後に読み直すと、
最大60秒間ふるい内容が返り得る。**これは楽観ロックを直接壊す**（4.2 に対処を書く）。

### 2.5 その他

| 確かめたこと | 結果 |
|---|---|
| 存在しないパスの GET | `404` |
| ディレクトリ一覧の各要素 | `name` `path` `sha` `size` `type` を返す。**`content` は返さない** |

## 3. 仕様から確認したこと（未実測）

出典は GitHub REST API ドキュメント（`apiVersion=2022-11-28`）。

### 3.1 `PUT /repos/{owner}/{repo}/contents/{path}`

- 引数は `message`（必須）、`content`（必須・base64）、`sha`（**更新時のみ必須**）、`branch`
- 応答は更新後の**コンテンツ（新しい `sha` を含む）とコミット**の両方を返す
- 状態コード: `201` 新規作成 / `200` 更新 / `409` Conflict / `422` Validation failed / `404`

**`409` が文書に挙がっていることが、疑問1に対する仕様上の裏付けである。**
ただし**「どの条件でどれが返るか」は文書に明記が無い。**
とくに次の2つは書かれていないので、実測しなければ確定できない。

- 既存パスへ `sha` 無しで PUT したとき（`422` と予想。設計書 8.1 の3行目）
- 存在しないパスへ `sha` 付きで PUT したとき（`404` か `422` か。同表の5行目）

### 3.2 サイズ

| 条件 | 可否 |
|---|---|
| 1 MB 以下 | この endpoint の全機能が使える |
| 1〜100 MB | `raw` / `object` メディアタイプのみ |
| 100 MB 超 | 非対応 |

マップの `.md` は現状最大でも数十 KB なので**制約にならない**。

### 3.3 レート制限 ⚠️

| 種別 | 上限 |
|---|---|
| プライマリ（認証済み） | 5,000 リクエスト/時 |
| セカンダリ・同時実行 | 100 |
| セカンダリ・ポイント | 900 ポイント/分 |
| セカンダリ・**内容を作る要求** | **80/分 かつ 500/時** |

**最後の行が自動保存に直撃する。** 保存1回 = コミット1つ = 内容を作る要求1つ。
**500/時 は、平均して7.2秒に1回の保存が上限**という意味である。
現在の自動保存は入力が止まってから 800ms で走る（`src/state/workspace.ts`）。
GitHub を保存先にしたまま同じ間隔で書くと、集中して編集した1時間で上限に達する。

## 4. 実装に効く判断（2.6-3 への申し送り）

### 4.1 保存間隔を保存先ごとに変える（必須）

3.3 の 500/時 に対し、`LocalFolderStore` と同じ 800ms は使えない。
`MapStore` 側に「推奨する保存間隔」を持たせ、`src/state/` の自動保存がそれに従う形にする。
**判断は `src/state/` に置く**（描画層に書かない、という規約どおり）。

なお `LocalFolderStore` の 800ms は変えない。ローカル書き込みに上限は無い。

### 4.2 書き込み直後に読み直さない（必須）

2.4 の60秒キャッシュがあるため、`write()` の戻り値を
**PUT の応答に入っている新しい `sha` から作る。** 読み直して確認してはいけない。

読み直しが避けられない箇所（次項の競合時）では `fetch(url, { cache: "no-store" })` を
使い、それでもなお GitHub 側の配信キャッシュが残る可能性を織り込む。

### 4.3 競合時にサーバの内容を取りに行く必要がある（必須）

`ConflictError` は `serverVersion` と **`serverMd`（サーバ側の本文）** を伴う契約であり、
契約テスト（`src/store/__tests__/contract.ts` の
「baseVersion が古いと ConflictError を投げ、サーバ側の内容を伴う」）がこれを検査する。

**409 の応答本文には現在の内容が入らない。** よって 409 を受けたら
改めて GET して本文を取る。ここが 4.2 のキャッシュと最も噛み合わないので、
`no-store` を付けるのはとくにこの経路である。

### 4.4 `list()` は「軽量」にならない ⚠️

`MapMeta` は `title` `tags` `created` `updated` を持ち、いずれも frontmatter にしか無い
（`src/core/types.ts`）。ところが 2.5 のとおり**ディレクトリ一覧は `content` を返さない。**

したがって `GitHubStore.list()` は **1 + N リクエスト**になる。
設計書 8.1 の「本文は読み込まない（軽量）」という注釈は、GitHub では字義どおりには満たせない。

読み取りはプライマリ枠（5,000/時）なので数十マップなら破綻しないが、往復回数が素直に効く。
**2.6-3 で決めること:** 一覧を IndexedDB にキャッシュし、
2.3 の条件付き GET（`If-None-Match` に前回の `sha`）で差分だけ取り直す。
ディレクトリ一覧に `sha` が入っているので、**本文を取らずに「どれが変わったか」までは判る。**

### 4.5 base64 変換に `btoa` を使わない（必須）

`content` は base64 で渡す。**`btoa()` は Latin-1 しか扱えず、日本語で例外になる。**
`TextEncoder` でバイト列にしてから base64 にする。復号も対称に `TextDecoder` を使う。
本ツールの本文は日本語が前提なので、ここは踏むと必ず壊れる。

## 5. 残っていること（利用者のトークンが要る）

**疑問1「Blob SHA が楽観ロックとして機能するか」は、まだ確定していない。**
409 が文書に挙がっているという裏付けまでで、実際の挙動は書き込まないと判らない。

確かめるのは設計書 8.1 の `write()` 契約表そのもので、**5行のうち4行**が対象。

| # | baseVersion | 保存先の状態 | 期待する挙動 | 予想する応答 |
|---|---|---|---|---|
| 1 | `null` | 存在しない | 新規作成 | `201` |
| 2 | `null` | 存在する | `ConflictError` | `422`（要確認） |
| 3 | 版を指定 | 一致 | 上書き | `200` |
| 4 | 版を指定 | 不一致 | `ConflictError` | `409`（要確認） |
| 5 | 版を指定 | 存在しない | `MapNotFoundError` | `404` か `422`（要確認） |

あわせて確かめること。

- 認証済みの条件付き GET（304）が枠を消費するか（2.3 は未認証での実測）
- PUT の応答に入る `sha` が、送った内容の blob ハッシュと一致するか
- PUT 直後の GET が新しい内容を返すまでの実際の遅れ（2.4 の60秒がどう効くか）

**必要なもの:** 検証用の空リポジトリ1つと、そこだけに絞った Fine-grained PAT。
権限は **Contents: Read and write のみ**でよい。
検証が済んだらトークンは失効させ、2.6-2 では利用者自身が入力する形にする。

**注意:** 本文書とリポジトリにトークンを書かない。検証時は環境変数で渡す。
