## 1. プロジェクトの目的と成功基準

### 1.1 目的

考えを整理するためのマインドマップツールを構築し、その成果物を摩擦なくAIへの入力ドキュメントとして利用できる状態にする。

### 1.2 成功基準

本プロジェクトは以下を全て満たしたときに成功とする。

| # | 基準 | 判定時期 |
|---|---|---|
| S-1 | 自分の実際の思考整理に日常的に使っている（週3回以上） | Phase 1 完了 + 2週間後 |
| S-2 | AIに渡すMarkdownを、コピー1操作で得られる | Phase 1 完了時 |
| S-3 | 保存したファイルが破損・変質した事例がゼロ | 全期間を通じて継続 |
| S-4 | 既存ツール（紙・テキストエディタ等）に戻りたいと思わない | Phase 2 完了 + 2週間後 |
| S-5 | 外出先のスマートフォンから編集できる | Phase 3 完了時 |

**S-1 と S-4 は主観的だが、本プロジェクトにおいては最も重要な基準である。** 個人ツールは「使い続けられるか」が唯一の価値尺度であり、機能数ではない。

### 1.3 明示的な非目標

- 他者への公開・配布
- 収益化
- 機能の網羅性（設計書 2.2 の対象外リストを守る）

## 3. フェーズ構成

**基本方針: 各フェーズの完了時点で「実際に使える状態」になっていること。** 全部完成するまで使えない、という進め方は取らない。

```
Phase 0 ── 基盤・変換エンジン ────── 内部品質の土台（利用者からは見えない）
   │                                 ここでR-01（データ変質リスク）を潰す
   ▼
Phase 1 ── 編集機能 ──────────────── ★ここから実用開始
   │                                 Windowsで日常的に使える
   ▼
Phase 2 ── 管理・出力・PWA ───────── ★日常ツールとして完成
   │                                 ここで実利用に入り、改修要望が出た
   ▼
Phase 2.5 ─ 言葉と導線 ───────────── 実装済み機能の見え方を直す
   ▼
Phase 2.6 ─ 置き場所（GitHub） ───── ★保存先が増える
   ▼
Phase 2.7 ─ スマートフォン ───────── ★どこでも使える（2.6 に依存）
   ▼
Phase 2.8 ─ 見る手段と戻る手段 ───── Markdown 表示・履歴
   ▼
Phase 2.9 ─ 編集操作 ─────────────── 親子の反転・アウトラインD&D
   ▼
Phase 2.10  記法の表示 ───────────── 表と装飾を読める形にする
   ┊
   ┊ （見送り）
   ▼
Phase 3 ── AWS同期 ──────────────── GitHub で足りなければ検討する
```

**Phase 2.7 が 2.6 に依存する理由:** スマートフォンで動かない原因は画面の崩れではなく
**保存先が無いこと**である。File System Access API はデスクトップ版 Chromium にしか無く、
レスポンシブ対応だけを先に行っても使える状態にはならない。

### フェーズ定義

| Phase | 名称 | 目的 | 完了時にできること |
|---|---|---|---|
| 0 | 基盤・変換エンジン | 最大リスクの先行解消 | （利用者向け機能なし） |
| 1 | 編集機能 | 最小限で実用に到達する | マップを作り、編集し、`.md` で保存し、AIに渡せる |
| 2 | 管理・出力・PWA | 日常ツールとして完成させる | 複数マップの管理・検索、AI出力3モード、インストール |
| 2.5 | 言葉と導線 | 使い方が分かる状態にする | ボタン名と作成手順から迷いが消える（**2026-09-02 完了**） |
| 2.6 | 置き場所（GitHub） | 保存先の制約を外す | GitHub リポジトリの `.md` を直接編集できる（**2026-09-03 完了**） |
| 2.7 | スマートフォン | 場所の制約を外す | スマートフォンから編集できる |
| 2.8 | 見る手段と戻る手段 | 不安なく書き換えられるようにする | `.md` を直接見られる、過去の版へ戻せる |
| 2.9 | 編集操作 | 構造の組み替えを速くする | 親子の反転、アウトラインのD&D |
| 2.10 | 記法の表示 | 書いた内容を読める形にする | 表と装飾がそのまま見える |
| 3 | AWS同期 | （見送り） | Phase 2.6・2.7 で目的が満たせるため保留 |

**Phase 0 を先に置く理由:** 設計書 R-01 の「Markdownラウンドトリップの不整合によるデータ変質」は本プロジェクト唯一の致命的リスクである。UIを作った後にこれが発覚すると、データモデル全体の作り直しになる。**最も不確実で最も影響の大きい部分を最初に確定させる。**

**プロパティテストが検出した往復破壊（いずれも単体テストでは到達し得ない入力）**

| 事象 | 原因 |
|---|---|
| 空白のみのノートが空行として出力され消える | パーサ側だけが正規化しており、シリアライザと非対称だった |
| `<html>` で始まる行が破棄される | HTMLブロックとして解析され段落にならない |
| ルートの絵文字が往復で増える | frontmatter の title 由来の絵文字を H1 で上書きしていなかった |
| 空ラベルの子ノードが親のノートに吸収される | 空の箇条書きは段落を中断できない（CommonMark） |
| `=` のみの行が直前の行を見出しに変える | setext 見出しの下線は1文字でも成立する |
| `0x0` などのタグが消える | YAML では16進数として数値に解釈される。引用符判定を正規表現で行っていた |
| ラベル `! #` が `!` になる | ATX 見出しの閉じシーケンスとして末尾の `#` が除去される |

後半2件は10万件規模の実行で初めて再現した。**プロパティテストの実行回数を1万件で固定せず、変換規則を変更した際は一時的に数十万件まで上げて確認すること。**

### Phase 2.5〜2.10 — 実利用からの改修（2026-09-02 追加）

Phase 2 を実機で使った結果まとまった改修要望に対応する。**Phase 3（AWS同期）は当面見送る。**

## 7. 品質計画

### 7.1 テスト戦略

| 層 | 手法 | 対象 | 基準 |
|---|---|---|---|
| 変換エンジン | プロパティテスト（fast-check） | ラウンドトリップの冪等性 | ランダム木構造1万件が全て通過 |
| 変換エンジン | 単体テスト（Vitest） | パーサ・シリアライザ・AI出力の個別ケース | カバレッジ90%以上 |
| 永続化層 | 単体テスト（`MemoryStore` で代替） | `MapStore` の契約（楽観ロック含む） | 全メソッド網羅 |
| 永続化層 | 手動シナリオ試験 | 権限失効・外部変更・保存中断・競合 | 設計書11章の全事象 |
| UI | 手動試験 | キーボード操作の全ショートカット | 設計書 7.4 の全項目 |
| 性能 | 実測（DevTools Performance） | 1000ノードでの操作 | NF-01 / NF-02 / NF-03 |
| 全体 | ドッグフーディング | 実際の思考整理での使用 | 各マイルストーン後に2週間 |

**自動テストは変換エンジン（`src/core/`）に集中投下し、UIは手動試験に委ねる。** 個人ツールにおいてUIのE2Eテストを整備する費用対効果は低い一方、データ変質は取り返しがつかないためである。

**未解決: 全体実行が1回だけ1件落ちた（2026-09-02）。** 直後の再実行を含め、以降の
全体実行は全て通過している。**どのテストが落ちたのかを取り逃した**（出力の末尾しか
残していなかった）ため、原因は特定できていない。

ラウンドトリップのプロパティテストだけは疑いを晴らしてある。単独で7回連続実行し、
約10万件の乱択入力が全て通過した。プロパティテストは乱数の種が毎回変わるので、
稀な反例があればこの回数で現れる見込みが高い。**残る候補は偽タイマーを使う
非同期テストである**（`autosave` / `editor` / `LocalFolderStore`）。

再発時に原因を掴めるよう、**全体実行の出力は末尾だけを見ずに保存すること。**
fast-check は失敗時に種と反例を表示するため、出力さえ残っていれば再現できる。

### 7.2 コード品質の機械的強制

| ルール | 手段 |
|---|---|
| UI層は `MapStore` 以外の永続化APIを直接呼ばない（NF-51） | ESLint の `no-restricted-imports` で `src/views/**` からの FSA API / AWS SDK の import を禁止 |
| `mm` 配下以外に表示情報を書かない（原則2） | シリアライザの単体テストで検証 |
| mind-elixir への直接依存を局所化 | `src/views/Canvas/` 以外からの import を ESLint で禁止 |
| 型の厳格性 | `strict: true`、`noUncheckedIndexedAccess: true` |

### 7.3 各フェーズ共通の完了確認

各フェーズ終了時に以下を確認する。

1. DoD の全項目にチェックが入っている
2. `npm run build` / `npm run test` / `npm run lint` が全て成功する
3. 設計書との差異が発生していれば、設計書を更新している
4. 実データを使った動作確認を済ませている
