# OSS ライセンスの選択（2026-09-05・提案）

**種別: アイディアドキュメント（提案）。まだ決定していない。**
決めたら `LICENSE` を作り、`package.json` を直し、この文書に結論を追記する。

---

## 1. 前提の確認（実測）

**依存はすべて許容型で、どのライセンスを選んでも衝突しない。**

配信物に入る依存を推移的に数えた結果（2026-09-05、`npm ls` ではなく
各 `package.json` の `license` を集計）。

| ライセンス | 数 |
|---|---|
| MIT | 47 |
| ISC | 1 |
| **コピーレフト系（GPL / MPL / EPL など）** | **0** |

主要な依存は `mind-elixir` 5.15.1（MIT）、React（MIT）、`remark-parse`（MIT）、
`zustand`（MIT）、`yaml`（ISC）。**制約は無い。純粋にこちらの意思で選べる。**

## 2. このプロジェクト固有の事情

ライセンスを一般論で選ばない。**Mieru には他と違う事情が3つある。**

### 事情1: 信頼の説明が「読めること」に依存している

Mieru はブラウザだけで動き、利用者の GitHub トークンを扱う。
**配信されたコードがブラウザの中でその鍵に触れられる**という性質は避けられない。
だから README では「OSS なので配っているコードが全部読める」と説明している。

**この説明は、改変版が配られたときに崩れる。**
誰かが Mieru を改変してトークンを盗む版をホストしたとき、
**許容型ライセンスでは、その改変を公開する義務が無い。**

### 事情2: 静的サイトなので「配布」の形が特殊

サーバのソフトウェアではなく、ブラウザへ配られる JavaScript である。
**利用者の手元には既にビルド済みのコードが届いている**（読もうと思えば読める）。
この性質が、コピーレフトの効き方を普通のアプリと変える。

### 事情3: 目的は普及であって収益ではない

「OSS として提供して市場に貢献したい」というのが出発点である。
**囲い込む相手がいない。** 商用利用を止めたい動機も無い。

## 3. 選択肢

### 案A: MIT

**最も普及していて、最も短く、最も摩擦が少ない。**

| | |
|---|---|
| 良い点 | 誰でも何にでも使える。**採用の障壁がゼロ。** 企業の法務が止めない。依存にする側も気にしない |
| 良い点 | 短く、読めば分かる。説明が要らない |
| 悪い点 | **改変版を非公開でホストできる。** 事情1の穴が塞がらない |
| 悪い点 | 特許について何も言わない |
| 近い例 | `mind-elixir`、markmap、React、Obsidian プラグインの多く |

### 案B: Apache License 2.0

**MIT にほぼ等しく、特許条項と変更点の明示が加わる。**

| | |
|---|---|
| 良い点 | MIT の利点をほぼ保ったまま、**明示的な特許許諾**が付く。企業が採用しやすい |
| 良い点 | 改変したファイルに変更を示す義務がある（弱い透明性） |
| 悪い点 | 本文が長い。個人プロジェクトには重い |
| 悪い点 | **事情1の穴は塞がらない**（ホストしても開示義務は無い） |
| 近い例 | Kubernetes、Swift、Android |

### 案C: GNU AGPL v3

**改変してネットワーク越しに使わせる者に、ソース公開を義務づける。**

| | |
|---|---|
| 良い点 | **事情1に正面から効く。** 改変版をホストする者は、その改変を公開しなければならない |
| 良い点 | この分野の先例が厚い。**Logseq と Joplin がどちらも AGPL-3.0** |
| 良い点 | 「読めるから信用できる」という説明が、**善意の約束から法的な義務に変わる** |
| 悪い点 | **採用の障壁になる。** 多くの企業が AGPL を社内規定で禁じている |
| 悪い点 | **静的サイトでは効き方が不確実。** AGPL 13条は「ネットワーク越しに対話する利用者」への提供義務を課すが、**ブラウザで動くコードにどう当てはまるかは確立した解釈が無い** |
| 悪い点 | 部品として取り込みにくくなる。`src/core/` の変換エンジンだけ使いたい人が使えない |

### 案D: MPL 2.0

**ファイル単位のコピーレフト。** 改変したファイルだけ公開すればよい。

| | |
|---|---|
| 良い点 | AGPL より摩擦が小さく、MIT より透明性がある |
| 悪い点 | **ネットワーク条項が無い。** ホストするだけなら開示義務が生じない。**事情1に効かない** |
| 悪い点 | 中間的で説明が要る。採用側が判断に時間を使う |

### 案E: 分ける（`src/core/` は MIT、アプリ全体は AGPL）

| | |
|---|---|
| 良い点 | 変換エンジンは部品として広く使ってもらい、アプリ本体は改変の公開を求める |
| 悪い点 | **説明と運用が複雑になる。** 個人プロジェクトで管理しきれない |
| 悪い点 | いま `src/core/` を部品として求めている人はいない。**問題が起きてから分ければよい** |

## 4. 推奨

### **案A（MIT）を推奨する。**

事情1を重く見るなら AGPL だが、**AGPL を選ぶ理由が2点で崩れる。**

**理由1: AGPL は狙っている脅威を実際には止めない。**
守りたいのは「改変版が利用者のトークンを盗む」ことである。
**そういうことをする者は、ライセンスも守らない。**
AGPL が効くのは善意の改変者に対してだけで、
**悪意の改変者に対しては何の防御にもならない。**
実際の防御は別のところにある。専用 Organization からの配信（NF-44）、
CSP による通信先の限定、外部リソースを読み込まないこと。
**これらは既に実装済みで、ライセンスに頼っていない。**

**理由2: 静的サイトへの AGPL 13条の適用が不確実である。**
効くかどうか分からない条項のために、確実な採用障壁を払うことになる。

そのうえで **MIT を選ぶ積極的な理由が3つある。**

- **目的が普及だから。** 収益化も囲い込みもしない以上、摩擦を減らす方に倒す
- **依存が全て MIT / ISC だから。** 生態系に揃う
- **短いから。** 「配っているコードは全部読める」という説明と、
  読めば分かる短いライセンスは相性が良い

### 案B（Apache-2.0）を選ぶなら

**特許を明示的に扱いたい場合、または企業での採用を明確に見込む場合。**
Mieru には特許になるような発明が無く、いま企業導入の見込みも無いので、
**現時点では MIT の簡潔さを取る方が良い。**

## 5. 決めたときにやること

| # | 作業 |
|---|---|
| 1 | `LICENSE` をリポジトリ直下に置く（著作権者名と年を入れる） |
| 2 | `package.json` の `"private": true` を外し、`"license": "MIT"` を足す |
| 3 | `package.json` に `repository` `homepage` `keywords` `description` を足す |
| 4 | README の「ライセンス」節を書き換える |
| 5 | GitHub のリポジトリ画面にライセンスが表示されることを確認する |

**`"private": true` を外すのは npm へ公開するためではない。**
これが付いていると意図が「非公開」と読めるためで、
外したうえで publish しない運用にする（そもそも publish するパッケージではない）。

## 6. 著作権表示について

`LICENSE` に入れる名義を決める必要がある。**個人名か、`mieru-app` か。**
将来ほかの貢献者が加わったとき、`Copyright (c) 2026 <名前> and contributors`
の形にしておくと、都度の書き換えが要らない。
