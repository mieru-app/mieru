## 1. 計測の範囲

**この報告で埋まっているのは変換と編集ロジックだけである。** 描画（mind-elixir）と
ファイル入出力は Node 上では測れないため、ブラウザでの実測が残っている。
「全部測った」ことにしないよう、3章に未測定の項目を明示する。

| 環境 | 内容 |
|---|---|
| 計測方法 | `npm run perf`（`scripts/perf.test.ts`、`vitest.perf.config.ts`） |
| 実行環境 | Windows 11 / Node.js v20.20.0 |
| 試料 | 1011 ノード（第1階層10 × 第2階層10 × 第3階層9、各第2階層にノート1件） |
| 値 | 20〜50 回の**中央値**。1回の外れ値に引きずられないようにしている |

**この計測は `npm test` に含めない。** 時間を測る検証は実行環境の負荷で揺れ、
稀に落ちるテストになる。常用の門には入れず、変換規則を変えたときに手で走らせる。

## 2. 計測結果（1000ノード）

| 処理 | 実測 | 目安 | 判定 |
|---|---|---|---|
| `parseMarkdown`（読み込み） | **75.03 ms** | 100 ms | ○ |
| `serializeMarkdown`（保存） | **0.84 ms** | 50 ms | ○ |
| `exportMarkdown`（AI 出力・見出し展開） | **0.97 ms** | 50 ms | ○ |
| `addChild`（編集1回） | **0.19 ms** | 16 ms | ○ |
| `removeNode`（部分木の削除） | **0.13 ms** | 16 ms | ○ |
| `collapsedUidsToPaths`（折り畳みの保存形式への変換） | **0.60 ms** | 50 ms | ○ |
| `queryIndex`（1打鍵ぶんの絞り込み・20マップ） | **0.34 ms** | 16 ms | ○ |
| `buildMapIndex` ×20（索引の作成） | **1619.89 ms** | 2000 ms | △ |

編集操作の目安を 16 ms にしているのは、これを超えると1操作で1フレーム落ちるためである（60fps = 16.6 ms/フレーム）。

### 分かったこと

**編集は十分に速い。** 木の操作は 0.2 ms 未満であり、1000 ノードでも
60fps の予算（16.6 ms）の 1% しか使わない。**残りはすべて描画側の問題である。**
NF-01 が満たせないとすれば原因は mind-elixir の再描画であって、編集ロジックではない。

**保存は速く、読み込みが重い。** シリアライズが 0.84 ms なのに対し、
パースは 75 ms と 90 倍近い。`remark-parse` による mdast の構築と、
`position` を使った元ソースの切り出しの分である。
自動保存（800 ms デバウンス）に対して 0.84 ms は無視できる。

**いちばん重いのは索引の作成（1620 ms / 20マップ）。**
1マップあたり約 81 ms で、その大半が `parseMarkdown` である。
全文検索の索引は本文を行として舐めるのではなく `parseMarkdown` を通しており
（ラベルとノートを区別し、エスケープを解いた状態で載せるため）、その代償になっている。

緩和はしてある。`SearchIndex.refresh` は `MapStore.list()` が返す version を鍵にして
**内容が変わったマップだけを読み直す**（`src/state/search.ts`）。
1620 ms が掛かるのはフォルダを開いた直後の1回だけで、以降の編集では
書き換えた1マップぶん（約 81 ms）しか掛からない。

**それでも初回の待ちは残る。** ただし全文検索の想定規模は計画上まだ未決であり
（`docs/project-plan.md` Phase 2）、「1000ノードのマップを20個」は実際の使い方より
かなり重い想定である。実利用で本当に遅いと感じてから手を入れる。
手を入れるなら、索引専用の軽いパーサを書くのではなく
**索引の作成を分割して画面を止めないようにする**方が筋がよい（正しさの経路を二重に持たない）。

## 3. 未測定（ブラウザでの実測が要る）

| ID | 要件 | なぜ未測定か |
|---|---|---|
| NF-01 | 1000ノードで編集操作が 60fps | mind-elixir の再描画時間を含む。Chrome DevTools Performance が要る |
| NF-02 | 初回描画 500ms 以内 | 上と同じ。パース 75 ms を差し引いた 425 ms が描画の予算になる |
| NF-03 | 入力停止から 800ms 後に保存を開始し 200ms 以内に完了 | File System Access API の書き込み時間を含む |
| NF-20 | オフラインで起動・閲覧・編集 | Service Worker の動作確認。機内モードで実施する |
| NF-32 | PWA としてインストールでき独立ウィンドウで起動 | 実機確認 |

### 実測の手順

1. `npm run build` して `npm run preview`（Service Worker は本番ビルドでのみ登録される）
2. 1000ノードのマップを用意する。`scripts/perf.test.ts` の `bigMarkdown()` が生成する
   Markdown をそのまま `.md` として保存先フォルダへ置けばよい
3. DevTools → Performance で記録しながら `Tab` / `Enter` を連打し、フレーム落ちを見る（NF-01）
4. Performance で再読み込みし、`init` から最初の描画までを測る（NF-02）
5. Network を Offline にして再読み込みし、起動と編集ができることを確かめる（NF-20）
