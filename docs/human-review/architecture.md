# アーキテクチャ解説

**読む人: このリポジトリを初めて見る開発者。**
コードを1ファイルずつ読んでも見えてこない「構造」と「意図」を説明する。
実装時に参照する正本は [設計の索引](../design.md) にある。

---

## 1. 何のための道具か

### 1.1 背景

考えを整理する手段としてマインドマップを用いたい。加えて、整理した内容を**AIに読ませる入力ドキュメント**として活用したい。

既存のマインドマップツール（XMind, MindMeister 等）は独自形式で保存し、Markdown出力は劣化を伴う二次的なエクスポート機能である。そのため「整理する」と「AIに渡す」の間に必ず変換の手間と情報欠落が発生する。

### 1.2 目的

本ツールは **Markdown を保存形式そのものとする** ことでこの断絶を解消する。マインドマップの編集結果は常に人間可読な `.md` ファイルとして存在し、AIへの入力は「そのファイルを渡す」だけで完了する。

### 1.3 達成目標

| # | 目標 | 検証方法 |
|---|---|---|
| G-1 | マインドマップの作成・編集・管理ができる | Phase 2 完了時に実利用で評価 |
| G-2 | AI入力用Markdownをワンアクションで出力できる | Ctrl+Shift+C の1操作で完了すること |
| G-3 | Windows PCで快適に動作する | 1000ノードで60fps維持 |
| G-4 | スマートフォンでも編集できる | Phase 2.7 完了時 |
| G-5 | UI/UXがシンプルで使いやすい | モード2つ・ツールバー1本・モーダル原則禁止の遵守 |
| G-6 | **他の人も、自分の GitHub リポジトリを保存先にして使える** | OSS として配信し、利用者が自分のトークンで自分のリポジトリを読み書きできること（2.3） |

## 2. 何をやり、何をやらないか

### 2.1 対象

- マインドマップの作成・編集・削除・一覧・検索
- キャンバス表示とアウトライン表示の相互切替、および Markdown そのものの表示（Phase 2.8）
- Markdown ファイルへの永続化（Phase 1: ローカルフォルダ / Phase 2.6: GitHub リポジトリ）
- テキスト出力（形式 × 範囲の2軸。7.3）と、AI からの取り込み指示のコピー（Phase 2.5）
- PWAとしてのインストールとオフライン動作
- スマートフォンからの編集（Phase 2.7。保存先を GitHub に置くことで成立する）
- 過去の版の閲覧と復元（Phase 2.8）
- Markdown 記法の描画（Phase 2.10。保存形式には影響しない）
- **OSS としての配信と自己ホスト**（Phase 2.6。2.3）

### 2.2 対象外

| 項目 | 判断理由 |
|---|---|
| 複数人でのリアルタイム共同編集 | 同時編集の発生頻度が低く、CRDT導入の複雑さに見合わない。利用者が増えても**各自が自分のリポジトリを使う**ため、共同編集の必要は生じない |
| 画像・添付ファイルの埋め込み | Markdownの可搬性を損なう。画像はURL参照のみ許容 |
| 手描き・自由配置キャンバス | ツリー構造の明快さが目的。Excalidraw等の代替が存在する |
| プレゼンテーション機能・印刷レイアウト | 目的が思考整理であり成果物提示ではない |
| AIによる自動マップ生成 | 「自分で考える」ことが目的のため意図的に除外（将来検討） |
| 課金・サーバ側のマルチテナント | **サーバを持たないため成立しない。** 各利用者のデータは各利用者の GitHub リポジトリにあり、アプリは静的ファイルとして配られるだけである（2.3） |


**なお 2026-09-03 に OSS 配信を決定したため、当初の「他者への公開・配布はしない」
という非目標は撤回されている。** 信頼境界の変化は
[セキュリティ](../design/security.md) にある。

## 3. 全体の構成


```
┌─────────────────────── Windows PC ───────────────────────┐
│                                                          │
│  Edge / Chrome（PWAとしてインストール）                   │
│  ┌────────────────────────────────────────────────────┐  │
│  │  Mieru (React SPA)                              │  │
│  │  ┌──────────────┐  ┌──────────────┐                │  │
│  │  │ キャンバス表示 │  │ アウトライン  │  ← 同一モデルの2ビュー
│  │  │ (mind-elixir) │  │ 表示          │                │  │
│  │  └──────┬───────┘  └───────┬──────┘                │  │
│  │         └────────┬──────────┘                      │  │
│  │            ┌─────▼──────┐                          │  │
│  │            │  MapDoc    │  メモリ上のモデル           │  │
│  │            └─────┬──────┘                          │  │
│  │        ┌─────────▼──────────┐                      │  │
│  │        │  Markdown 変換層    │  md ⇄ Model          │  │
│  │        └─────────┬──────────┘                      │  │
│  │        ┌─────────▼──────────┐                      │  │
│  │        │  MapStore (I/F)    │                      │  │
│  │        │   └ LocalFolderStore                      │  │
│  │        └─────────┬──────────┘                      │  │
│  └──────────────────┼─────────────────────────────────┘  │
│         File System Access API                           │
│  ┌──────────────────▼─────────────────────────────────┐  │
│  │  利用者が指定したフォルダ                            │  │
│  │   例: D:\Documents\mindmaps\                       │  │
│  │       ├ 新規事業の論点整理.md                       │  │
│  │       └ 読書メモ_思考の整理学.md                    │  │
│  └────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────┘

サーバなし・ログインなし・外部通信なし
```


**この図は現行の構成である。**「Phase 1 構成」という題で書かれていたが、
Phase 2.6 で保存先に `GitHubStore` が加わった以外、形は変わっていない。

### 保存先が増えても形が変わらない理由

UI は `MapStore` インターフェースだけを知る（[設計原則](../design/principles.md) 原則3）。
`LocalFolderStore` と `GitHubStore` は同じ契約テストを通しており、
**差し替えても UI・編集ロジック・変換エンジンに手が入らない。**

### データの流れ

```
利用者の入力
  → src/views/（描画と入力）
  → src/state/（何が起きるべきかの判断・Undo/Redo・自動保存の間合い）
  → src/core/（モデル → Markdown 文字列）
  → src/store/（MapStore → ローカルフォルダ or GitHub）
```

読み込みは逆向きに流れる。**依存は一方向で、逆流させない。**
`src/state/` は React にも `mind-elixir` にも依存しない。だから自動テストが書ける。

## 5. 採った判断と、捨てた選択肢

### 12.1 キャンバスライブラリ: mind-elixir を採用

| 候補 | 最新版 | 評価 | 判断 |
|---|---|---|---|
| **mind-elixir** | 5.15.1（安定） | MIT。編集・キーボード操作・折り畳み・横断リンクを内蔵。フレームワーク非依存。活発に更新（2026-08時点） | **採用** |
| markmap | 0.18.12 | MIT。Markdown→マインドマップの描画品質は高いが**表示専用で編集不可** | 不採用。ただし記法互換の参照元とする |
| @xyflow/react | 12.11.5 | 汎用ダイアグラム。自由度は最大だがマインドマップのレイアウト・操作を全て自作する必要がある | 不採用（工数過大） |
| jsmind | 0.9.1 | 実績はあるがUIが古く、更新頻度が低い | 不採用 |

**バージョン固定の注意:** mind-elixir は 6.0.0 系がプレリリース中であり、npm の `latest` タグが `6.0.0-next.4` を指すという異常な状態にある（dist-tags: latest=6.0.0-next.4, beta=6.0.0-next.5）。安定版の `5.15.1` を `package.json` で厳密に固定し、6.0 系の安定版リリース後に計画的に移行する。

**ロックイン対策:** データは Markdown であり mind-elixir に依存しない。将来このライブラリを捨てても、描画層を差し替えるだけで済む。これは原則1が生む副次的な利益である。

### 12.2 Markdownシリアライザを自前実装する理由

`remark-stringify` は箇条書き記号やインデント量の出力が設定と入力に依存して揺れる。6.5 の強保証（バイト単位の冪等性）を達成するには出力を完全に制御する必要があるため、解析には `remark-parse` を使い、生成のみ自前で実装する。

### 12.3 CRDT（Yjs等）を採用しない理由

CRDTはリアルタイム共同編集のために設計された技術であり、データモデルに相応の複雑さを持ち込む。本ツールは単一利用者が自分の複数端末で使うことを想定しており、同時編集の発生頻度は極めて低い。8.5 の「両方を保持して利用者に選ばせる」方式で必要十分であり、費用対効果が見合わない。


**サーバレスにした理由**は AWS 前提の記述だったため
[AWS 同期](./aws-sync.md) へ移した。**現状はサーバそのものが無い。**

## 6. リスク


| ID | リスク | 影響 | 発生度 | 対策 |
|---|---|---|---|---|
| R-01 | Markdownラウンドトリップの不整合によりデータが変質する | **致命的** | 中 | Phase 0 で最優先実装。プロパティテスト1万件で検証。弱保証時は保存前に必ず警告（6.5） |
| R-02 | mind-elixir 6.0 移行時の破壊的変更 | 中 | 中 | 5.15.1に固定。ラッパーコンポーネントを1枚挟み、直接依存箇所を局所化する |
| R-03 | File System Access API の権限失効でデータを失う | 大 | 中 | IndexedDBへの退避を必ず経由する（11章） |
| R-04 | Phase 1 が Edge/Chrome 限定である | 中 | 確定 | 仕様として明示。Phase 3 で解消 |
| R-05 | 大規模マップ（1000ノード超）での描画性能劣化 | 中 | 中 | Phase 1 完了時に性能試験を実施。必要なら仮想化・折り畳み既定化を導入 |
| R-06 | Phase 3 で S3 の条件付き書き込みが利用できない | 小 | 低 | ETag比較の2段構えにフォールバック（8.4） |
| R-07 | スマートフォンでのキャンバス操作が実用に耐えない | 中 | **高** | 設計として織り込み済み。スマートフォンではアウトライン形式を既定とする（F-43） |
| R-08 | 仕様が肥大化しUIの簡潔さが失われる | 中 | 中 | 2.2 の対象外リストと第3章の設計原則を判断基準として維持する |
| R-09 | 配信オリジンに別のページが公開され、**利用者のトークンが読まれる** | **致命的** | 低 | 専用 Organization に分離し、そこに Mieru 以外を公開しない（8.6・NF-44） |
| R-10 | 利用者が権限の広いトークンを作り、事故時の被害が広がる | 大 | 中 | アプリ内で作成手順を案内し、1リポジトリ・Contents のみ・期限付きを既定の説明とする（8.7.3） |
