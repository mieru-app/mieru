## 1. なぜ実装より先にこれを置いたか

設計書 8.1 の `write(id, md, baseVersion)` は「`baseVersion` が保存先の現在の版と
不一致なら `ConflictError`」という契約を持つ。`GitHubStore` はこれを Blob SHA で
満たす計画である。

**この2点が崩れると `GitHubStore` は成立しない。**

1. Blob SHA が楽観ロックとして機能するか（不一致を GitHub 側が拒めるか）
2. Blob SHA が内容に対して安定か（同じ内容なら常に同じ値になるか）

実装を書いてから崩れると、認証・UI まで含めて組み直しになる。先にここだけを確かめた。

**結論: 2つとも成立する。** ただし契約表5行のうち1行は GitHub 単体では満たせず、
実装側で1リクエスト補う必要がある（3.3）。その補い方が 4.1 で、
**副作用としてレート制限と競合時の本文取得の問題も同時に解ける。**

## 2. Blob SHA は内容から決まる（疑問2）✅

### 2.1 `sha` は git の blob ハッシュそのものである

公開リポジトリへの未認証の読み取りで確認した。API が返した `content` を base64 復号し、
`sha1("blob " + 長さ + "\0" + バイト列)` を計算すると、API の `sha` と完全に一致する。

| ファイル | サイズ | API の sha | 再計算した blob ハッシュ | 一致 |
|---|---|---|---|---|
| `README.md` | 4,286 B | `aad3c4b0f7a71ea9…` | `aad3c4b0f7a71ea9…` | ✅ |
| `docs/design.md` | 59,676 B | `2623d08c246fa23d…` | `2623d08c246fa23d…` | ✅ |

**書き込み側でも同じだった。** 後述の検証で PUT した2回とも、応答に入っていた新しい `sha` が
送ったバイト列の blob ハッシュと一致した（`dc2b2135…` と `8834aa23…`）。

**つまり `version` はサーバが振る不透明な値ではなく、内容だけで決まる関数である。**

### 2.2 その帰結

**同じ内容なら、パスが違っても、コミットが違っても、時刻が違っても同じ SHA になる。**

これは `LocalFolderStore` が内容ハッシュを version にしているのと**同じ性質**であり
（設計書 8.2 の注記）、副次的な利点もそのまま受け継ぐ。

- 外部から**同じ内容**で書き直されても競合にならない。
  **実測でも、同じ内容を再保存したら `200` が返り `sha` は変わらなかった**
- 逆に、A → B → A と戻された場合は元の version に戻る（いわゆる ABA）。
  ただし戻った先の内容は自分が読んだ内容と同一なので、上書きしても失うものが無い。
  `LocalFolderStore` と同じ理屈で受容できる

### 2.3 ブラウザから直接呼べる（CORS）✅

**構成全体がこの前提に乗っているので、明示的に確かめた。**

```
Access-Control-Allow-Origin: *
access-control-allow-methods: GET, POST, PATCH, PUT, DELETE
access-control-allow-headers: Authorization, Content-Type, If-Match,
  If-None-Match, If-Modified-Since, ..., X-GitHub-Api-Version
Access-Control-Expose-Headers: ETag, ..., X-RateLimit-Remaining, ...
```

`PUT` の事前確認（preflight）も `204` で通る。**中継サーバが要らない。**
`If-None-Match` が許可ヘッダに、`ETag` が公開ヘッダに含まれているため、
**4.1 の条件付き GET はブラウザからそのまま実装できる。**

ここが塞がっていれば `GitHubStore` は中継サーバを必要とし、
「サーバレス（Lambda不使用）」という判断（設計書 12.4）ごと崩れていた。

## 3. 楽観ロックは機能する（疑問1）✅

検証用リポジトリ `kyritk/mieru-api-test` に対し、設計書 8.1 の `write()` 契約表5行を
そのまま叩いて実測した（2026-09-03）。**消費したレート枠は 25。**

### 3.1 実測結果

| # | baseVersion | 保存先の状態 | 契約上の挙動 | 実際の応答 | 判定 |
|---|---|---|---|---|---|
| 1 | `null` | 存在しない | 新規作成 | `201` | ✅ |
| 2 | `null` | 存在する | `ConflictError` | `422` | ✅ 写せる |
| 3 | 版を指定 | 一致 | 上書き | `200` | ✅ |
| 4 | 版を指定 | 不一致 | `ConflictError` | `409` | ✅ 写せる |
| 5 | 版を指定 | 存在しない | `MapNotFoundError` | **`201`** | ❌ **写せない** |

応答本文のメッセージ。

- **#4**: `verify/t1.md does not match dc2b2135a8a398b2470f35040a48135557e3943f`
- **#2**: `Invalid request.` / `"sha" wasn't supplied.`

**4行目が本命だった。** 古い `sha` を付けて PUT したら `409` で拒まれ、上書きは起きなかった。
**楽観ロックは Blob SHA で成立する。**

### 3.2 409 の応答本文に現在の内容は入らない ⚠️

`ConflictError` は `serverVersion` と **`serverMd`（サーバ側の本文）** を伴う契約であり、
契約テスト（`src/store/__tests__/contract.ts` の
「baseVersion が古いと ConflictError を投げ、サーバ側の内容を伴う」）がこれを検査する。

**409 の本文はメッセージだけなので、本文は別途取りに行く必要がある。**

### 3.3 存在しないパスに `sha` を付けても、無視して新規作成される ❌

**契約表5行目が満たせない。** 存在しないパスへ `sha` 付きで PUT したところ、
`404` でも `422` でもなく **`201` が返り、ファイルが作られた。**
GitHub は「作成時は `sha` を見ない」という実装になっている。

**これは黙ってデータを復活させる。** 想定される事故はこうなる。

> スマートフォンでマップを削除する
> → パソコン側はそのマップを開いたまま（削除を知らない）
> → 自動保存が走る
> → **削除したはずのマップが復活する**

契約が `MapNotFoundError` を求めているのは、まさにこれを利用者に知らせるためである。
**GitHub 単体では区別できないので、実装側で1リクエスト補う**（4.1）。

## 4. 実装に効く判断（2.6-3 への申し送り）

### 4.1 保存の前に「条件付き GET」を1回入れる（必須・最重要）

`baseVersion` が `null` でないとき、PUT の前に
**`If-None-Match: "<baseVersion>"` を付けた GET** を1回投げる。応答で3つに分岐する。

| 応答 | 意味 | すること |
|---|---|---|
| `304` | 存在し、読んだときから変わっていない | そのまま PUT する |
| `200` | 存在するが、他所で変わっている | `ConflictError`。**本文はこの応答に入っている** |
| `404` | 他所で削除された | `MapNotFoundError` |

**これ1つで3つの問題が同時に片付く。**

- **3.3 の穴が塞がる。** `404` を見てから PUT しないので、削除済みを復活させない
- **3.2 の本文取得が要らなくなる。** 競合を見つけた時点で `200` の本文を持っている。
  409 を受けてから改めて取りに行くより往復が1回少ない
- **`304` はレート枠を消費しない。** 実測で `X-RateLimit-Used` が 16 → 16 のまま動かなかった。
  **競合していない通常の保存では、この確認は事実上ただである**

PUT 側の `409` は残しておく。この GET と PUT のあいだに他所が書き込む可能性は消せないため、
**最後の砦として 409 も `ConflictError` へ写す。**

### 4.2 自動保存の間隔を保存先ごとに変える（必須）

GitHub のセカンダリ制限は **内容を作る要求が 80/分 かつ 500/時**（仕様書）。
保存1回 = コミット1つ = 内容を作る要求1つなので、
**500/時 は平均7.2秒に1回の保存が上限**という意味になる。

現在の自動保存は入力が止まってから 800ms で走る（`src/state/workspace.ts`）。
**GitHub にこのまま使うと、集中して編集した1時間で上限に達する。**

`MapStore` 側に「推奨する保存間隔」を持たせ、`src/state/` の自動保存がそれに従う形にする。
**判断は `src/state/` に置く**（描画層に書かない、という規約どおり）。
`LocalFolderStore` の 800ms は変えない。ローカル書き込みに上限は無い。

なお 2.2 のとおり**内容が変わっていなければ `sha` も変わらない**ので、
保存前に内容の同一性を見て要求そのものを省ける。枠の節約になる。

### 4.3 書き込み直後に読み直さない（必須）

GET の応答には**60秒のキャッシュ**が付く。

```
Cache-Control: private, max-age=60, s-maxage=60   （認証済みの場合）
Cache-Control: public,  max-age=60, s-maxage=60   （未認証の場合）
```

**サーバ側の伝播は速い。** PUT 直後の GET は 0.38 秒で新しい内容を返した。
**問題になるのはブラウザのキャッシュだけ**である。`fetch()` はこの指示に従うため、
書き込み直後に同じ URL を読むと最大60秒ふるい内容が返り得る。

- `write()` の戻り値は、**PUT の応答に入っている新しい `sha` から作る。** 読み直さない
- 4.1 の条件付き GET には `cache: "no-store"` を付ける。
  ここでふるい応答を掴むと**競合の判定そのものが狂う**

### 4.4 `list()` は「軽量」にならない ⚠️

`MapMeta` は `title` `tags` `created` `updated` を持ち、いずれも frontmatter にしか無い
（`src/core/types.ts`）。ところが**ディレクトリ一覧は `sha` と `size` は返すが `content` を返さない。**

したがって `GitHubStore.list()` は **1 + N リクエスト**になる。
設計書 8.1 の「本文は読み込まない（軽量）」という注釈は、GitHub では字義どおりには満たせない。

読み取りはプライマリ枠（5,000/時）なので数十マップなら破綻しないが、往復回数が素直に効く。
**2.6-3 で決めること:** 一覧を IndexedDB にキャッシュし、
ディレクトリ一覧の `sha` を前回と突き合わせて**変わったものだけ本文を取り直す。**
一覧1回で「どれが変わったか」までは判るので、変化が無ければ追加の往復は 0 になる。

### 4.5 ファイル取得の ETag は blob SHA と同じ値である

`GET /contents/<path>` の `ETag` は、同じ応答の `sha` と一致した
（`"dc2b2135a8a398b2470f35040a48135557e3943f"`）。

**`version` をそのまま `If-None-Match` に渡せる。** 変換も対応表も要らない。
4.1 がこの性質の上に成り立っている。`watch?()` を作る場合も同じ手段が使える。

### 4.6 base64 変換に `btoa` を使わない（必須）

`content` は base64 で渡す。**`btoa()` は Latin-1 しか扱えず、日本語で例外になる。**
`TextEncoder` でバイト列にしてから base64 にする。復号も対称に `TextDecoder` を使う。
本ツールの本文は日本語が前提なので、ここは踏むと必ず壊れる。

### 4.7 サイズは制約にならない

| 条件 | 可否 |
|---|---|
| 1 MB 以下 | この endpoint の全機能が使える |
| 1〜100 MB | `raw` / `object` メディアタイプのみ |
| 100 MB 超 | 非対応 |

マップの `.md` は現状最大でも数十 KB。

## 5. 検証の後始末（2026-09-03）

- 検証用リポジトリに作ったファイルは**すべて削除した**（`verify/t1.md`、`verify/none.md`）
- 利用者のトークンは**検証終了時に削除**した。GitHub 側での失効も依頼済み
- **トークンは本文書にもリポジトリにも記録していない**
- 検証スクリプトはプロジェクト外（作業用ディレクトリ）に置いた。リポジトリには入れない

**再検証したくなった場合**は、空リポジトリ1つと、そこだけに絞った Fine-grained PAT
（Contents: Read and write のみ）があれば5分で再現できる。3.1 の表がそのまま手順である。
