# UI 層の規約

仕様の正本は `docs/design.md` の7章（機能設計）。

## 依存の制約

**IMPORTANT: この層から File System Access API・AWS SDK・IndexedDB を直接呼んではいけない。** 永続化は `MapStore` 経由のみ（設計原則3。非機能要件 NF-51 として ESLint でも禁止する）。

- `mind-elixir` を import してよいのは `src/views/Canvas/` のみ。ラッパーを1枚挟み、他所は自前の型だけを見る
- ライブラリ固有の型を `src/core/` のモデルの代わりに使い回さない

## UI の簡潔さを守る

以下は設計上の意図的な制約であり、実装の都合で崩さない（設計原則4）。

- **画面のモードは3つまで**（キャンバス／アウトライン／Markdown）。4つ目を足さない。
  **内訳は「書き換える画面が2つ、読む画面が1つ」で、この比率を崩さない。**
  並び順・押しボタンの字・`Ctrl+E` の巡回は `src/state/view-mode.ts` が一手に持つ。
  ここで手書きすると、押しボタンには出ているのにキーでは辿り着けない表示が生まれる
- **ツールバーは1本**。ボタンを増やす前に、キーボードショートカットで済まないかを検討する
- **モーダルダイアログは削除確認を除いて使わない**
- **保存ボタンを置かない。** 自動保存（入力停止から800ms）とし、状態はステータスバーに常時表示する
- 全ての主要操作をキーボードだけで完結できること。ショートカット一覧は `docs/design.md` 7.4

## 状態

- 編集操作は Undo/Redo スタック（50段）に必ず積む。積まない変更経路を作らない
- キャンバスとアウトラインは同一モデルの2つのビューである。表示ごとに別の状態を持たせない
- 表示を切り替えても選択ノードを維持する

## エラー表示

- 権限失効・保存失敗・外部変更は、モーダルではなくステータスバーで通知し、その場で復帰操作を提供する
- 変換不可な要素があるファイルを保存する前には、破棄される内容を提示して確認を取る

## 実機でしか分からなかったこと（Phase 2.7、設計書 7.2.1）

**IMPORTANT: `mind-elixir` は実機の指では動かなかった。拡大縮小も移動も自前で用意した**
（`src/views/Canvas/`）。**pointer イベントを使い `touch-action: none` を自分で置き
`move`/`scale` も公開しているのに、指では動かなかった。** ライブラリの対応可否を
API の存在で判断しないこと。移動の判定は `pan.ts` に切り出してテストがある。

**訂正（2026-09-04）: 原因の説明は誤りだった。** ここには「移動は
`pointerType === "mouse"` で門番されている」と書いてあったが、5.15.1 の実際の式は
`!e.editable || t.button === o && t.pointerType === "mouse" || t.pointerType === "touch"`
で、**末尾に `|| t.pointerType === "touch"` がある**（引用時に落としていた）。
ライブラリ側は指でのパンを受け付ける。**動かなかった事実は実機で確かめたとおりだが、
理由は未解明である。** 二重に効いている疑いがあるので、`pan.ts` を触るときは
**指1cm に対して地図が2cm動かないか**を先に実機で見ること。

- **`mind-elixir` はキャンバス要素の `className` を `"map-container"` で上書きする。**
  あの要素にクラスを書いても消える。大きさ・`touch-action: none`・`font-size: 16px` は
  向こうの CSS が持っている
- **狭い画面の判断は `src/state/layout.ts` に置く。** 「起動時にサイドバーが開いている」
  「枝を触るたびにノート欄が地図を覆う」「一覧を開いたまま設定を押すと何も出ない」は
  どれも CSS では直らない。**幅の境目を持つのは `NARROW_MAX_WIDTH` ひとつだけにする。**
  CSS のメディアクエリに同じ値を書くと、片方だけ直したときに黙ってずれる
- **iOS Safari は 16px 未満の入力欄で自動拡大する。** 本文が 14px なので全部が対象になる
- **IMPORTANT: 構造編集の入口はキーボードにしか無かった**（7.4 で `mind-elixir` の
  右クリックメニューとツールバーを切ってあるため）。**指しか無い端末では読むことしか
  できなかった。** 狭い画面用の編集バーを足して塞いだ。並べる操作は `src/app/edit-bar.ts`。
  **この一覧が嘘をつくとその端末では操作が失われる**ので、`keymap.ts` などと同じく
  描画層にありながら自動テストを持つ
- **2.7 を「レイアウトの問題」として立てたのが誤りだった。** 実際の壁は入力手段である。
  **画面の広さは見えるが、入力手段が無いことは画面を見ても分からない。**
  同種の判断をするときは「指だけで最初から最後まで通せるか」を先に問うこと

## 判断を描画層に書かない

この層は自動テストを持たないため、**判断を書いた分だけ検証できない領域が増える**。

- 「このキーで何が起きるか」は `src/app/keymap.ts`（割り当て）と `src/state/commands.ts`（実体）に書く
- 「木をどう変えるか」は `src/state/tree.ts` に書く
- 「保存すべきか」は `src/state/autosave.ts` に書く
- コンポーネントは、それらを呼んで結果を描くだけにする

props のコールバックは `onChange: (v: string) => void` の形で書く。
メソッド短縮記法（`onChange(v: string): void`）は `@typescript-eslint/unbound-method` に掛かる。

## テスト

この層は自動テストを整備せず手動試験に委ねる（`docs/project-plan.md` 7.1）。
代わりに、変更したら `npm run dev` で実際に操作して確認すること。最低限、
キーボードショートカット全項目（`docs/design.md` 7.4）と、
保存・外部変更・競合の3つの状態表示を通すこと。

ただし mind-elixir との相互変換（`src/views/Canvas/adapter.ts`）は純粋関数であり、
自動テストの対象とする。ここが壊れるとキャンバスで1回操作しただけで
ノートや横断リンクが消えるため、手動試験に委ねてよい種類の処理ではない。
